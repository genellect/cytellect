# PR の前の確認

この手順は PR の作成・push の許可を与えない。PR は依頼されたときだけ作り、`main` へのマージ・デプロイ・配布・有料サービスの利用は、オーナーがその対象を指示した場合を除いて行わない（`AGENTS.md`）。

## 1. 最新の main を取り込む

`git fetch origin main` のあと、`origin/main` を merge または安全な rebase で取り込む。他者の変更とまだコミットしていない作業は保持する。

## 2. 検証

`cytellect-verify` を実行する。同じコミットで記録した結果があれば再利用する。画面を変えた場合は `cytellect-screen-check` の結果もそろえる。

## 3. 差分のレビュー

| 変更 | レビュー |
|---|---|
| すべてのコードの変更 | `/code-review medium` で自分の差分を確かめる |
| 測定・統計・検出・作図の計算（`packages/analysis`、`engines`、`services/api` の測定と統計） | `/code-review high` |
| 認証・招待・セッション、アップロードの許可、LLM・GPU など外部への送信、ログ、更新と署名、workflow とシークレット、配布物の境界 | 上に加えて `/security-review` |
| 文書だけ | レビューは省き、リンクと文書間の矛盾を確かめる |

- `max` の水準と Workflow は、依頼された場合だけ使う。
- 指摘は再現やコードで確かめてから直す。今の変更の範囲の外にある指摘は、PR の「残る課題」に書く。
- PR へのコメント投稿（`--comment`）は、依頼された場合だけ行う。

## 4. 研究データと秘密情報

- 差分に、非公開の研究画像・正解の輪郭・論文・ファイルパス・研究結果・参加者情報、認証情報・トークンがないか確かめる。画像やバイナリを加えた場合は `uv run python scripts/check_public_tree.py` を実行する（`dev.py check python` に含まれる）。
- 見つけた場合は内容を引用せずに依頼者に知らせ、コミットから除く。push 済みなら履歴の扱いを依頼者に確認する。
- スクリーンショットは公開画像の画面だけにする。

## 5. 文書

- 方針・仕様・手順・動作を変えた場合は、関連する文書（`README`、`docs/requirements.md`、`docs/methods.md`、`SECURITY.md`、`docs/security.md`、`CONTRIBUTING.md`、`docs/ci.md` など）を同じ PR で更新したか確かめる。
- 計画と未完了の受入条件は `docs/roadmap.md` に記録する。セッションごとの引き継ぎ文書は作らない。
- 文書間の矛盾を見つけた場合は、自分の判断で直さず、事実を照合してオーナーに確認する。

## 6. PR の説明

`.github/pull_request_template.md` の見出しをすべて使い、日本語または英語で書く。

- 「検証」には実行したコマンドと結果を書き、手元・CI・本番・非公開データでの確認を分ける。未実施と失敗は、合格と区別して書く。
- 「科学的な影響」と「本番・配布への影響」は、なければ「なし」と書く。
- 「残る課題」に、確かめられなかった条件と、この PR で扱わない点を書く。
- 説明の最後に、システムが指定する帰属の行を付ける。
