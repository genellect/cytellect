# PR の作成

変更を伴う作業は、PR の作成までを標準とする（`CLAUDE.md`「作業の完了」）。PR の作成に、マージ・デプロイ・配布・有料サービスの利用の許可は含まれない（`AGENTS.md`）。

## 1. 最新の main を取り込む

`git fetch origin main` のあと、`origin/main` を merge または安全な rebase で取り込む。他者の変更とまだコミットしていない作業は保持する。

## 2. 検証

`cytellect-verify` を実行する。同じコミットで記録した結果があれば再利用する。画面を変えた場合は `cytellect-screen-check` の結果もそろえる。時間のかかる検証は、終わるのを待たずに PR を作り、未完了として書いてよい。CI が同じ検査を実行する。

## 3. レビュー

`CLAUDE.md`「目的別のスキル」の表に従い、変更に当てはまるものだけを PR ごとに 1 回実行する。

- ロジックの変更があれば `/code-review medium`（計算は `high`）。画面の見た目・文言・文書・設定・試験だけなら実行しない。
- 認証・認可、アップロードの受け入れ、更新の署名、workflow の権限とシークレットを変えた場合だけ `/security-review`。
- 指摘は再現やコードで確かめてから直す。今の変更の範囲の外にある指摘は、PR の「残る課題」に書く。

## 4. コミットの中身

`git diff --stat origin/main...HEAD` で、追加したファイルを見る。認証情報と、研究室の画像・測定表などのデータファイルがコミットに入っていないことだけを確かめる。画像の登録は CI の公開ツリーの検査が確かめる。境界は `CLAUDE.md`「研究データの境界」に従う。

## 5. 文書

- 方針・仕様・手順・動作を変えた場合は、関連する文書を同じ PR で更新したか確かめる。
- 計画と未完了の受入条件は `docs/roadmap.md` に記録する。セッションごとの引き継ぎ文書は作らない。
- 文書間の矛盾を見つけた場合は、自分の判断で直さず、事実を照合してオーナーに確認する。

## 6. PR を作る

`.github/pull_request_template.md` の見出しをすべて使い、日本語または英語で書く。

- 「検証」には実行したコマンドと結果を書き、手元・CI・本番・非公開データでの確認を分ける。未実施と失敗は、合格と区別して書く。
- 「科学的な影響」と「本番・配布への影響」は、なければ「なし」と書く。
- 「残る課題」に、確かめられなかった条件と、この PR で扱わない点を書く。
- 説明の最後に、システムが指定する帰属の行を付ける。

PR を作ったら、URL と検証の結果を依頼者に報告する。既に PR がある場合は、新しく作らずに説明を更新する。
