# 変更に対応する検証

手元では変更に関係する検査だけを短く実行し、全体は PR の CI に任せる。コマンドの正本は `CONTRIBUTING.md` の「PR を出す前に」と `scripts/dev.py`。

## 1. 実行する

```bash
python3 scripts/dev.py check --related
```

`origin/main` との差分（コミット済み、まだコミットしていない変更、追跡していないファイル）から、次を選んで実行する。`origin/main` が古い場合は、先に `git fetch origin main` を実行する。

- Python：lint、型、変更したファイルを読み込む・名指しする試験
- Web と提案 Worker：型と lint、変更したファイルを読み込む単体試験
- API や解析を変えたとき：契約（OpenAPI、既定レシピ、TypeScript の型）がコミットと一致すること
- 文書とスキル：リンク、`dev.py` のコマンド、スキルの参照、公開ツリー

何が選ばれるかだけを見るときは `python3 scripts/dev.py changed` を使う。

変更によって、次を足す。

| 変更 | 足すもの |
|---|---|
| API | `python3 scripts/dev.py contracts`。生成したファイルを同じコミットに入れる |
| 依存パッケージ・lockfile | `python3 scripts/dev.py audit`。秘密情報の走査は件数だけを報告する |
| 解析エンジン | `python3 scripts/dev.py check --fiji` |
| 画面 | `cytellect-screen-check` |

全体を手元で実行するのは、CI の失敗を再現するときと、依頼があったときだけ（`python3 scripts/dev.py check --changed`）。

- 時間のかかる検証は `run_in_background` で実行し、完了の通知を待つ。
- 同じコミット・同じ条件で記録した合格は、その後の変更で無効にならない限り再利用してよい。再利用したことを報告に書く。

## 2. 失敗したとき

- 原因は出力・ソース・再現で特定する（`docs/development-principles.md` の「問題への対処」）。推測で直さない。
- 合格させるために、試験を消す・飛ばす・期待値を書き換える・閾値を緩めることはしない。試験の期待値が誤っていると判断した場合は、根拠を示して依頼者に確認する。
- 評価データに合わせた閾値やモデルの調整で合格させない。

## 3. 報告する

次の 4 つを分けて、日本語で報告する。

- **合格**：実行したコマンドと、対象のコミット
- **失敗**：コマンド、失敗した試験、出力の要点、特定した原因（未確定ならそう書く）
- **未実施**：実行しなかったものと理由
- **CI に任せる**：手元で実行しなかった全体の試験と、CI だけのジョブ

未実施・失敗を合格として書かない。
