# 画面の確認

画面の変更は、試験の合格だけでなく、実際に表示して確かめる。クラウドの開発セッションでは登録済みの公開画像を使う。隔離ローカル環境では、オーナーが指定した範囲で研究室の画像でも確かめてよい。PR に貼るスクリーンショットは公開画像の画面にする（`docs/development-principles.md` の「研究データと検証」）。

## 1. 道筋と起動の方法を選ぶ

変更した画面が関わる研究者の道筋を、`docs/usability-tasks.ja.md` の課題から選ぶ。研究者による評価と同じ道筋を確かめるためで、課題の「参加者への課題」と「自力完了の観察条件」を読んでから操作する。

| 変更した機能 | 課題 | 確かめる場所 |
|---|---|---|
| 計画、解析への引き継ぎ | 1 | ワークスペース、`bbbc013` |
| 画像の登録 | 2 | ワークスペース、`bbbc013` |
| 検出、領域の修正、測定 | 3 | ワークスペース、`bbbc013`（核の検出だけなら `bbbc007`） |
| 分布の図、元の画像に戻る | 4 | ワークスペース、または公開デモ |
| 群間比較、統計、図 | 5 | 公開デモの核数の場面。入力から確かめるときはワークスペース、`jump-plk1`（課題の人工の練習セットは使わない） |
| 陽性の判定と陽性率、核小体、画像の測定ビュー | 6 | 公開デモの核小体の場面 |
| LP | — | 公開のビルド |

起動の方法：

| 場所 | 起動 |
|---|---|
| LP、公開デモ（`/demo`） | `NEXT_PUBLIC_API_ORIGIN` を設定していないシェルで `pnpm build` を実行し、`pnpm --filter @cytellect/web start` で起動する。CI の公開サイトの試験と同じ構成で、API・Fiji・鍵は要らない。記録した結果で動くため、検出のやり直しや画像の追加は確かめられない |
| ワークスペース | `python3 scripts/dev.py doctor` で準備を確かめてから `python3 scripts/dev.py serve`。表示された招待コードで `http://localhost:3000/workspace` に入る。画像は `python3 scripts/dev.py public-inputs <名前>` で取得する（名前と内容は `CONTRIBUTING.md`「PR を出す前に」の表） |

- `NEXT_PUBLIC_API_ORIGIN` はビルドの時点で固定される。`serve` のビルドは API を指すため、公開デモとワークスペースを切り替えるときはビルドし直す（公開のビルドのあとに `serve --skip-build` を使わない）。
- サーバーは `run_in_background` で起動し、`curl --fail` で応答を確かめてから操作する。
- API の Origin は `localhost` を使う（`127.0.0.1` では照合に失敗する）。
- `doctor` が `[--]` を示した外部サービス（GPU、解析提案）は使わずに確かめ、使えなかったことを報告する。`doctor --live` は GPU を起動して課金されるため、依頼がない限り実行しない。

## 2. 操作して撮る

- Chromium と Playwright は環境に入っている。`require('playwright')` を使い、`playwright install` はしない。
- 選んだ課題の道筋を、最初から順にたどる。変更前と変更後を同じ手順で撮れる場合は両方撮る。
- デスクトップの幅（`apps/web/playwright.config.ts` の既定）と、スマートフォンの幅の両方で撮る。
- 自分で見るだけのスクリーンショットは `deviceScaleFactor: 1`、PR に貼るものは `2`。保存先は scratchpad で、リポジトリには入れない。
- ブラウザのコンソールのエラーと、失敗した通信を記録する。

## 3. 点検する

撮った画面を、`docs/development-principles.md`「画面と文章」の 4 つの問いと文言の規則（UC-01〜UC-07）に照らして、毎回確かめる。LP は `docs/lp-art-direction.md` の冒頭の優先順位に従い、オーナーの指示とデザインのスキルの判断を細目より優先する。

1. 何を対象に、何を測っているかが、画面から分かる。
2. 次の操作が 1 つに見える。
3. 結果から元の画像に戻って確かめ、直せる。
4. 修正と判断の導線に迷う箇所がない。

次のスキルは、当てはまる変更のときだけ使う。

| スキル | 使う変更 |
|---|---|
| `design:design-critique` | 新しい画面、画面の構成や導線の変更 |
| `design:accessibility-review` | 色分け、操作の方法、スマートフォンの配置の変更 |

- 研究者が自分のデータを見て判断できることを優先する。原画像・ファイル名・測定値を隠す、注意書きを足す、といった指摘は採らない。
- 指摘のうち、今の変更の範囲にあるものだけを直す。範囲の外のものは報告に挙げ、勝手に直さない。

## 4. 報告する

- たどった課題、確かめた場所と画像、画面の幅
- 4 つの問いのうち満たせていないものと、直したもの・直していないもの
- 確かめられなかったこと（外部サービスがない、公開デモでは確かめられない操作など）

「画面で確認した」と書くのは、実際に表示して確かめた範囲だけにする。これは自動の確認で、研究者による評価の代わりにはならない。
