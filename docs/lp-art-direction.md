# LP のデザイン方針

状態：2026-11-25、オーナーの判断で書き直した。LP の見た目、文章、素材の正本。

この文書は、LP の**方向**だけを決める。色の値、書体、文字の大きさと太さ、余白、配置、素材の種類は決めない。それらは、デザインを担う人やエージェントが今の表現の方向（[§4](#4-表現の方向)）に沿って選ぶ。選ぶときはページ全体で考え、判定はオーナーが実際の画面で行う。

## 1. 細目を固定しない理由

2026-10〜11 の方針では、判定を受けるたびに細目を規則として積み上げた。たとえば、文字は 1 色で太さは 500、地は白と淡い灰で差し色は桃色 1 色、主役は実写の映像、ヒーローの構成は変えない、などである。

その結果、新しい部品を作るときに、既存の見た目へ合わせることが先に立った。東京AIハッカソンの受賞を載せる作業では、それが原因で案が何度も不合格になった。細目は、その版に対する判定であって、次の版の要件ではない。

そこでこの文書では、どの版でも変わらない目的、誠実さ、品質の下限だけを固定する。表現の方向は数行の言葉で示し、刷新のたびに置き換える。置き換える前の方針は[記録](archive/lp-art-direction-2026-11.md)に残してある。

## 2. 目的（固定）

- LP の仕事は一つだけ。研究者に Cytellect を欲しいと思わせ、デモと導入へつなぐこと。
- 読者は、画像を扱う生命科学研究者の全体。研究者には利用価値を、エンジニアには技術の深さを伝える。
- 読者に起こしたい感情は二つ。自分の研究を論文に届けたいという志と、科学の未来に参加したいという気持ち。
- 迷ったときの基準は、「研究者がこれを見て欲しいと思うか」。

## 3. 守ること（固定）

### 言葉

- 誇張しない。根拠のない最上級、所要時間、数値を書かない。
- 機能、実績、推薦、利用者の声を創作しない。研究室の利用者の声は、本人が公開を承認するまで載せない。
- 主語は研究者にとっての利用価値にする。技術の名前や仕組みの説明から入らない。
- 測れるものを特定の構造に限って見せない。限って見せると、ほかの解析ができないプロダクトに見える。
- 否定、言い訳、防御的な注記、「開発中」の断りを置かない。評価を下げる留保も置かない。
- プロダクトの事実と矛盾させない。
  - 検出は独自の深層学習モデルで行う。「AI」と書くと LLM による設定提案と混ざって見える。
  - 追加学習そのものを売りにしない。
  - 「更新のたびにモデルが変わる」と読める書き方をしない。
- 数値は、何の値か直感的に分かるものだけを載せる。測定条件の異なるデータを根拠にしない。

### 素材

- 研究の記録やプロダクトの実績を装う素材を作らない。人物の顔、ロゴ、非公開の研究データを写さない。
- プロダクトの画面は公開デモから撮る。
- すべての素材の出典、ライセンス、加工内容を記録する。正本は次のファイル。
  - [`scripts/lp_film/sources.json`](../scripts/lp_film/sources.json)
  - [`photo-provenance.json`](../apps/web/public/marketing/photo-provenance.json)
  - `hero-film-provenance.json`
  - 公開資産の許可リスト
- 生成 AI の映像や画像は、オーナーがサービスを指定するまで使わない。

### 品質の下限

- 文字が読める。地とのコントラストは WCAG AA 以上にする。iPhone と Windows の画面で読める大きさと太さにする。
- 最初の画面で、約束と次の行動が分かる。
- 3D と映像は、どの環境でも成り立たせる。
  - 静止画の代替を用意する。
  - 省モーションの設定に従う。
  - 画面外にあるときと、タブが非表示のときは止める。
  - スマートフォンと、重い描画ができない端末でも成り立たせる。
- 縦に長くしない。機能は一度に一つ見せる形を基本にする。長いページは品質を下げるという判定を受けている。

## 4. 表現の方向

ここには方向だけを数行で書く。刷新のたびにオーナーの判断で置き換え、置き換えた版は PR の説明と [roadmap](roadmap.md) に残す。

**現在（2026-11-25〜）：3D の演出を中心にした、ダーク系のテーマ。見た人に感動を与えるもの。**

前の版の細目は、新しい方向で作るときに引き継ぐ義務がない。明るい地、桃色 1 色の差し色、実写を主役にすること、ヒーローの構成、書体がそれにあたる。残すかどうかは、作った画面を見て判断する。

## 5. 作り方

1. **役割を決める。** §2〜§4 と、作る部分が担う役割を、1〜2 文にまとめる。役割とは、読者に何を感じさせ、何をさせるか。
2. **方向から設計する。** frontend-design スキルを使う。既存のページに合わせるところから始めない。新しい部品も、ページの方向から設計する。そのうえで、前後の節との間合い、大きさ、重さをページ全体のバランスで決める。
3. **描いた案で方向を選ぶ。** 方向が分かれるときは、実際に描画した案を少数見せ、オーナーが選ぶ。静止画か短い試写でよい。言葉だけで合意して実装しない。
4. **ページ全体で作る。** 色、文字組み、レイアウト、3D、映像、動きを一つの方向で組み立てる。一部だけを差し替える修正を繰り返さない。HTML と CSS だけで絵を作らない。WebGL、Three.js、映像など、使える手段を制約せずに選ぶ。
5. **見せる前に批評する。** PC とスマートフォンの実際の画面で批評し（design-critique）、§3 の下限を確かめてから見せる。
6. **判定はオーナーが行う。** 実際の画面（Vercel のプレビュー）で判定する。エージェントの確認や試験の合格は、判定の代わりにならない。

参照サイトから倣うのは、デザインの水準だけにする。文章、内容、素材、配色は倣わない。参照サイトの多くは会社の LP だが、Cytellect の LP はプロダクトの LP で、目的が違う。

### 指摘の扱い

- 指摘は、その版が目的に届かなかった箇所として受け取る。理由を一般化して PR の説明に残し、細目の規則としては積み上げない（[開発の原則](development-principles.md#問題への対処)の「対症療法で直さない」）。
- 一つの指摘を直すときも、§2 と §3 のすべてに照らし直す。直前の指摘だけを見て直すと、別の判定を壊す。
- 方向そのものを変える判定は、§4 を書き換えて記録する。

## 6. 分担と記録

- 担当とブランチは、依頼ごとにオーナーが決める。2026-11 までの分担（映像は Codex、ページは Claude Code）は[記録](archive/lp-art-direction-2026-11.md#10-分担とファイルの境界)にある。
- 過去の試みと判定の経緯は[置き換える前の方針](archive/lp-art-direction-2026-11.md)にある。そこにある細目は、判定の理由を知るために読む。従うための規則ではない。
