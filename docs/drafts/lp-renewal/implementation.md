# LP の刷新：実装案

作成：2026-11-13。状態：案（オーナーの承認待ち）。2026-11-13 のオーナーの指摘と、その後の議論をまとめた。LP の見た目と素材の正本は [LP の美術方針](../../lp-art-direction.md)で、この案が承認されるまで美術方針が正しい。承認された変更は、実装と同じ PR で美術方針に反映する。

この文書は計画だけを扱う。コード、素材、公開サイトは変えていない。

## 1. 目的と範囲

### オーナーが示した課題（2026-11-13）

| 番号 | 課題 |
|---|---|
| (1) | 新機能との乖離。解析結果の要約や考察まで含めた、研究者 UX に特化した機能を訴求できていない。測れるパラメータが限定的に見える |
| (2) | 掲載画像が古い。現行の UI のスクリーンショットではない |
| (その他) | デザインが世界一流の LP の水準に届いていない |

### 目的

読み終えた研究者が、次の 2 つを現行の画面を見て納得していること。

- 自分の画像から、結果の要約と考察、論文の図まで行ける。
- 測りたいものを測れる。

### 変更の原則

変えるのは、上の課題に対する理由を示せる箇所だけにする（2026-11-13、オーナーの指示）。理由を示せない箇所は現行のまま残す。変える箇所と理由は [§3](#3-変えることと理由) に、変えない箇所は [§4](#4-変えないこと) に書く。

### 範囲

| 含む | 含まない |
|---|---|
| LP（`/`）の「できること」の節の中身と証拠、到達点を述べる文言 | ヒーロー映像（Codex の担当。美術方針 §9・§10） |
| LP の証拠に使う画面を撮る仕組み | 公開デモの作り直し、場面の追加、デモの画面や記録の変更 |
| 美術方針、ロードマップの更新 | 解析ワークスペース、`/demo`、`/plan`、`/download`、Windows 版 |

## 3. 変えることと理由

| 番号 | 変えること | 理由 |
|---|---|---|
| A | 「できること」の 4 タブの中身を、論文と同じ順の 5 段に替える（[§3.1](#31-できることの-5-段)） | 結果の要約と考察に居場所がない (1)。「測定」の段で指標の広さを示す (1) |
| B | 証拠を、すべて現行デモの解析結果の画面に替える。顕微鏡画像の合成は外す | 現行 UI の画面が 1 つもない (2)。素材は顕微鏡画像ではなく UI の解析結果とする（2026-11-13、オーナーの指摘） |
| C | 証拠は、全画面ではなく主張に対応する区画を、読める大きさで見せる。パネルは主張を上、画面を下にして幅を使う | 現行は縮小で文字が読めない (その他) |
| D | 最初に見えるタブを「結果」にする | 訴求したい要約が、押さないと見えない位置に隠れないようにする (1) |
| E | 到達点を述べる文言を、結論と考察まで伸ばす（[§3.2](#32-文言)） | どこも「論文の図まで」で終わっている (1) |
| F | 「できること」の節の入口に、明るい研究室で画面に向かう研究者の実写を 1 枚置く | 世界観に「結果を読み、考える時間」がない (1)、(その他)。素材は採用済みで、新しく探さない |
| G | 証拠の画面を撮るスクリプトと、撮影の記録（[§6](#6-素材を古くしない仕組み)） | 手作業の一度きりの撮影が、古くなった原因 (2) |

F は世界観に関わるので、実装の前に静止画でオーナーが判定する（[§5](#5-段階) の段階 1）。

### 3.1 「できること」の 5 段

タブの仕組み（一度に 1 つだけ表示、キーボード操作）は現行のまま使う。2026-10-23 の「長すぎる」という判定への対応を保つ。

| 段 | 主張（文案） | 画面（公開デモ） | 場面 | 課題 |
|---|---|---|---|---|
| 問い | やりたいことを一文で。解析の設定は、AI が組み立てます（現行の文） | AI に指示の例を選び、設定の候補が出た画面 | PLK1 | (2) |
| 測定 | 細胞一つひとつを、数・大きさ・形・明るさ・陽性率で | 核ごとの表（1 つの核の行に 13 列） | オキサリプラチン | (1) パラメータ |
| 結果 | 統計の結果は、結論の一文から | 結果のまとめ（結論、要点、実験回ごとの値） | PLK1 | (1) 要約 |
| 考察 | 解釈、ほかの説明、次に確かめることまで | 考察の枠 | PLK1 | (1) 考察 |
| 図 | 統計の検定も、論文に載せる図も、クリックだけで（現行の文） | グラフの画面（図と、幅・レイアウトの設定） | PLK1 | (2) |

- 場面と画面は、公開中のデモにあるものをそのまま撮る。デモは作り直さない。
- 結果の段の結論は「PLK1 KO で、視野あたりの核数が 79〜84% 減少」。3 回の実験すべてで同じ向きの記述統計で、注記なしで言い切れる。
- 測定の段だけ場面が違う。PLK1 の場面は染色が 1 つで、核ごとの表が 4 列しかないため。
- 現行の「自動検出」のタブにある検出の数値は、測定の段に現行のまま残す。現行の「解析の流れ」のタブは、5 段の並びそのものが流れを示すので置き換える。
- 各段の「デモで開く」は、その場面のその画面へつなぐ。ワークスペース ID は、リポジトリにある `apps/web/public/showcase/snapshot/scenes.json` からビルド時に場面の ID で引く。デモの側は変えない。
- 新しい文案は、美術方針 §11 の判定（短く言い切る 1 文、主語は研究者の利用価値、特定の構造に固定しない、否定と言い訳を書かない）に照らしてから確定する。

## 4. 変えないこと

次は、課題に対する理由を示せないので現行のまま残す。検討の途中で挙げた変更案のうち、見た目の推測にとどまるものは取り下げた。

| 箇所 | 取り下げた案 |
|---|---|
| 文字の大きさ | 使命の文を大きくする、見出しを 3 段階にする |
| 地の色と差し色 | 地を白と淡い灰にする、ミントをやめる |
| ヒーロー、使命の 2 文、ピペットの写真の帯 | 写真の帯を全面にする |
| 「どんな研究の画像も」の 4 項目 | 画面を添えた節に作り替える |
| 患者のカード、誘いのカード、ダウンロードの線 | 患者を全面の深緑に、誘いを白い地にする、線を外す |
| タブの仕組み | スクロールで段を切り替える |
| ナビゲーション、フッター、計測のイベント名 | — |
| 公開デモ | 場面の名前で開く URL、考察の例の追加、作り直し |

## 6. 素材を古くしない仕組み

1. **撮影をスクリプトにする。** 公開ビルドの `/demo` を開き、決めた場面と画面で、決めた区画（「結果のまとめ」「考察」など）だけを 2 倍の解像度で撮り、WebP で書き出す。画面の内容と値には手を加えない。PC 用とスマートフォン用を別に撮る。
2. **何を撮ったかを記録する。** 素材ごとに、場面の ID、画面、撮った区画、デモの `manifest.json` にある生成コミット（`generated_from_commit`）、SHA-256 を `provenance.json` に残す。

デモが更新されたときは、このスクリプトを走らせて撮り直す。記録とデモのずれを検査で止める案は、デモの作り直しの手順に手を入れるので、この案には含めない。

## 7. オーナーの判断が必要な点

| 番号 | 判断 | 推奨 |
|---|---|---|
| 1 | 考察を LP に載せる時期。本番では LLM の考察を有効にしていない（要件 AC-09）。デモの考察は「デモ用サンプル（参考）」の表示が付いた例 | 本番の有効化と同時に載せる。先に公開する場合は、考察の段を除いた 4 段で出す |
| 2 | ダウンロードの説明。公開中の Windows 版（0.1.0-local.21、2026-10-30 のコミット）には、結論の一文、核ごとの表、考察の枠が入っていない | 新しい版が出るまで、説明は現行のまま残す |
| 3 | 入口の実写（変更 F）。研究室の遠景の素材（`px-v-9573740`。ヒーローの 4 カット目の素材）から静止画を切り出して使う | 段階 1 の静止画で判定する |

別件の報告：美術方針 §11 は「92%」のような数値を載せないとしているが、現行の LP は「92% 核の検出精度」を載せている。この案では現行のまま残し、どちらが正しいかは決めていない。

## 8. 試験と検証

コマンドは [CONTRIBUTING](../../../CONTRIBUTING.md) に従う。

| 対象 | 確かめること |
|---|---|
| ヒーロー | 現行の検査をそのまま通す |
| 証拠の画像 | 5 段それぞれの画像が読み込まれ、縦横比が保たれ、どの幅でも横にはみ出さない |
| タブ | 最初に「結果」が見える。キーボードで 5 段すべてに届く |
| デモへのリンク | 各段のリンクが、その場面のその画面を開く |
| 計測 | 現行のイベント名が同じ操作で送られる |
| 公開ファイル | `python scripts/check_public_tree.py` |
| 文書 | `python3 scripts/check_docs.py` |

エージェントの確認と試験の合格は、判定の代わりにしない。見た目の判定は、段階 1 の静止画と段階 5 のプレビューでオーナーが行う（美術方針 §11）。

## 9. 危険と対策

| 危険 | 対策 |
|---|---|
| 製品の説明に寄って世界観を失う（2026-10-22 の再構成と同じ失敗） | 変えるのは「できること」の節の中だけ。ほかの節と世界観の素材は現行のまま |
| 製品の画面の青が、LP の色と合わない | 青の少ない区画（結果のまとめ、考察、表）を選ぶ。画面の色には手を加えない。段階 1 の静止画で確かめる |
| スマートフォンで画面の文字が読めない | PC 用の縮小を使わず、スマートフォンの幅で撮った素材を別に用意する |
| 並行作業との衝突。`apps/web/src/**` と `apps/web/tests/**` は、ロードマップの分担表で別の担当の範囲 | 段階 0 で分担表にこの作業を加えてから始める |
| デモの更新でリンク先や画面が変わる | リンクは場面の ID から引く。画面はスクリプトで撮り直す |
