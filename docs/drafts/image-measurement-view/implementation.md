作成：2026-11-11。[要件定義書（案）](requirements.md)の実装の手順。**要件がオーナーに承認されるまで実装を始めない。** 要件と食い違う場合は要件が正しく、この文書を直す。

## 1. 作業を始める前に

- [AGENTS.md](../../../AGENTS.md)、[要件定義書（案）](requirements.md)、[ワークスペースの再設計](../../workspace-redesign.md)の「Interaction model」を読む。

## 2. 方向性に照らしたレビュー（2026-11-11）

最初の案を、[プロダクトの使命](../../development-principles.md#プロダクトの使命)、[要件](../../requirements.md)の M22・M23、[ワークスペースの再設計](../../workspace-redesign.md)に照らして見直した。直した点は、要件定義書に反映済み。

| 使命・規則 | 最初の案の問題 | 直した点 |
|---|---|---|
| 「迷わず修正と判断を行い」 | 塗り分けるだけで、研究者がしきい値の妥当性を判断する材料がなかった | 撮影日ごとの判定値の分布としきい値を、右の領域に示す。選んだ核の値も示す（MV-04） |
| 右の領域は、いま選んでいるものの操作だけ（再設計） | 分類の操作を、画像の上の小窓に置こうとしていた | 分類の操作は右の領域に置き、色分けを選んだときに開く（MV-04） |
| 生物学的な妥当性を優先する（使命の約束） | Otsu を既定の判定方法として扱っていた | 本番では陰性対照による判定を先頭にし、手動・Otsu は探索的と明示する（MV-04） |
| M22「入力が変わったら明示的に判定し直す」 | 次の一手で、判定のやり直しを暗黙に行う案だった | 判定し直すことを、操作の名前と説明で押す前に示す（MV-09） |
| M23「対象・参照を明示する」 | 分配表を自動で読み込むと、対象と参照が見えなくなるおそれがあった | 既定の対象・参照を見出しに示して替えられるようにし、API への要求は明示のまま（MV-05、MV-06） |
| 余計な変更をしない（オーナーの指示） | 「新機能」の目印、機能の一覧、作業の流れの文章を足す案があった | どれも足さない。足すのは色分け 1 つと、次の一手 1 つだけ |
| 生物学的な妥当性を優先する | 「値の強さ」の色分けがあった | 入れない（判断 2） |

### 残る危険

- **表示が重くなる**：2 画面で、色分けごとに判定の記録と分配表を各視野で読む。読み込みは、その色分けを選んだときだけにする。N-03（開くまでの時間）は、既定の「輪郭」なら今と変わらない。
- **既存の試験への影響**：「区画への分配」ボタンと設定パネルの分類欄を使う試験は、書き換えが要る（[§5](#5-試験)）。
- **デモの記録が増える**：2 画面の両方の視野で、判定と分配表の応答を記録する。公開ファイルが増えるので、記録する組み合わせは既定の対象・参照と、判定できる染色に限る。

## 3. 今のコード（2026-11-11 の `main` と genellect/cytellect#194）

行番号は変わるので、部品と関数の名前で示す。場所はすべて `apps/web/src/components/workspace/review/` の下。

| 部品 | 今の役割 | 変える点 |
|---|---|---|
| `ConnectedWorkspace.tsx` の `Workspace` | 画像の画面の状態を持つ（`target`、`channelId`、`pairView`、`partitionView`、`channelSaved` など）。上部の操作の 1 行（`channelBar`）、`ImageStage`、`MeasurementsPanel`、`ConnectedPartition`、右の領域「画像解析」を描く | 色分けの状態（`colorBy`）を持つ。操作の行を 2 種類に分ける。`partitionView` と「区画への分配」ボタンをなくす。判定の復元を加える |
| `PairStage.tsx` | 2 画面の各画像と表を描く。`ReviewImageCanvas` に `classification` を渡していない。表に見出しがない。核ごとの表の切り替えを自分の状態に持つ | 色分けと判定・分配の結果を各画像に渡す。表の見出しを出す。核ごとの表の切り替えはワークスペースの状態に統一する |
| `ReviewImageCanvas.tsx` | 領域の輪郭を SVG の `path` で描く。`data-classification`（positive／negative／unknown）がある。選択中の領域には付かない | 5 状態と、核小体・核質の塗り分けの属性を描く。選択中の領域にも判定の色を残す |
| `review-image.module.css` | `.outline[data-classification=…]` の 3 状態の色。重ねて表示の線の色の指定が、判定の線の色より強い | 5 状態と核小体・核質の色。指定の強さを直す |
| `ConnectedChannelGate.tsx` | 右の領域の折りたたみの中にある。`POST /v1/workspaces/{id}/channel-gate` を呼ぶ。結果の `nuclei[]` に `status`、`channel_mean`、`threshold` がある | 色分けから開く節にする。判定値の分布としきい値の小さな図を加える。本番の方法の順を、陰性対照を先頭にする |
| `ConnectedPartition.tsx` | 「分配表を表示」で `GET /v1/revisions/{nuclear}/region-partition` を読み、結果を自分の中だけに持つ。1 視野だけ。開くと 1 画面になる | 結果をワークスペースに引き上げる。色分けで自動に読み込み、2 画面では各視野で読む |
| `MeasurementsPanel`、`MeasurementTable.tsx`、`NucleusTable.tsx` | 「このチャンネル／核ごとの表」の切り替えと見出し（1 画面だけ） | 表示中の表として、見出しと列を色分けで決める |
| `apps/web/src/lib/workspace/metric-catalog.ts` | 統計の指標を問いでまとめる | 次の一手で開く指標の対応に使う（新しい指標は加えない） |

今のコードの制約で、知っておくこと：

- 分類の結果は画面のメモリ（`channelSaved`）にだけある。GFP には読み込み時に記録を読み直す処理（`restoreClassification`）があるが、チャンネルの判定にはない。MV-10 では、この GFP の処理にならって復元を加える。
- 統計の画面の判定のやり直し（`ConnectedResults.tsx` の `classifyForResults`）は、比べる視野の版（cohort revision）に対して判定する。画像の画面の判定とは別の結果である。次の一手（MV-09）は、この統計の画面側の処理を呼ぶ。

各段階の終わりに、`python3 scripts/dev.py check web` と、関係するブラウザ試験を通してからコミットする。

## 8. 迷ったときの判断の基準

- 画像を見ている研究者が、次に何を知りたいかで決める。機能の名前や実装の都合で決めない。
- 新しく文章を足して解決しない。見え方（色・見出し・置き場所）で解決する。説明が要る場合は、開いて読む形にする。
- 計算をブラウザに足さない。足りない値は API と共通の解析が保存する。
- 判断に迷う科学的な点（しきい値・分母・向き）は、実装を止めてオーナーに確認する。
