# Windows 版の初回体験を直す：実装の手引き

作成：2026-11-25。対象の Issue：genellect/cytellect#284。状態：実装はまだ始めていない。この文書はコードを変えない。

Windows 版の Cytellect を初めて開いた研究者が、画像を入れて AI に質問するところまで進めない。Issue #284 は、オーナーがインストール版を実際に操作して見つけた問題を、画面の写真と時刻つきで記録している。この文書は、その問題をすべて直すための手引きである。経緯を知らない人やエージェントが、この文書だけを読んで作業を始められるように書いた。

## 1. はじめに読むこと

### 1.1 読む順番

1. この節（§1）で、アプリの構成と言葉を知る。
2. [§2](#2-決まっていること) で、もう決まっている方針を確かめる。古い文書と食い違うときは、§2 が正しい。
3. [§3](#3-issue-の項目と作業の対応) で、Issue のどの項目をどの作業（W1〜W12）が直すかを引く。
4. 担当する作業の節（[§6](#6-作業)）を読む。原因、直し方、完成の条件、試験、コードの場所がそこにまとまっている。
5. ほかの作業と共有するデータの形は [§5](#5-複数の作業が共有する設計) にある。

### 1.2 研究者に何が起きているか

Issue に書かれた体験を、短くまとめる。

- アプリを開くと、画像を入れる場所ではなく「実験デザイン」の選択が中央に出る。どのファイルをどこに入れればよいか分からない。
- 画像を選んでも「視野 0」のままで、何を受け取ったのかが見えない。続けて別の画像を選ぶと、先に選んだ画像が消える。
- 5 枚のうち 1 枚が壊れているだけで、正常な 4 枚まで巻き込まれる。群を指定して入れた画像が、その群に入らない。名前の表記が違うだけの 2 枚があると、全部の登録が止まり、選び直しても直らない。
- 登録できなかった画像について、研究者が「除外の理由」を書くよう求められる。ページを開き直すと、その画像は「名称不明」になり、何を除外するのかも分からない。
- 「この画像のチャンネル名を教えて。まだ測定はしないで」と AI に聞くと、「解析案が扱える形式ではありませんでした」と返る。答えはもらえない。
- 測定中かどうかが分からない。2 視野なのに進捗が「0/4」と出る。
- 更新の案内がどの画面にも出続け、閉じられない。

### 1.3 アプリの構成

Windows 版は、研究者の PC の中だけで動く Web アプリである。

| 部分 | 場所 | 役割 |
|---|---|---|
| 画面 | `apps/web`（Next.js、TypeScript） | ブラウザ（Edge）に表示する。`http://127.0.0.1:8765` で開く |
| ローカルの API | `services/api`（FastAPI、Python） | 画像の登録、解析の受付、保存。データは PC の中の SQLite とフォルダーに置く |
| 計算ワーカー | `services/api` の `local_worker.py` | 核の検出や測定を実行する別プロセス |
| ランチャー | `services/api/src/cytellect_api/local.py` | Windows で最初に開く小さな窓。API とワーカーを起動し、閉じると両方が止まる |
| 解析の共通実装 | `packages/analysis` | 測定・統計・解析案の検証。Windows 版もクラウド版も同じものを使う |
| AI の中継 | `services/proposal-worker`（Cloudflare Workers） | API の鍵を持ち、モデル（Claude）を呼ぶ。研究データは保存しない |

公開サイトの `/demo` は、同じ画面を記録済みのデータで動かすデモで、画像の追加を受け付けない。この文書が扱うのは Windows 版（本番）である。

画面は、上のタブ（実験・画像・統計・グラフ）、左の視野の一覧（下に「画像」「フォルダ」ボタン）、中央の作業領域、右のパネル（設定または AI）、下端の AI の入力欄でできている。

### 1.4 言葉

| 言葉 | 意味 |
|---|---|
| 視野 | 顕微鏡で撮った 1 つの場所。染色ごとの画像（チャンネル）が 1 つの視野にまとまる。コードでは field |
| チャンネル | 1 つの視野の中の、1 つの染色の画像。`C01`・`C02` のような番号や、`DAPI`・`GFP` のような染色名で区別する |
| 群 | 比べる条件。対照と処理など |
| 実験回 | 独立に行った実験の 1 回分。統計の n は実験回の数 |
| 実験デザイン | 群と実験回の構成。「実験」の画面で作る。「1 画面」は 1 群の記述、「2 画面」は 2 群の比較 |
| ワークスペース | 1 つの作業。画像、設定、結果をまとめて持つ |
| 解析版 | 検出と測定の結果。変更のたびに新しい版として保存する。コードでは revision |
| 候補と採用 | プレビューで作った結果は「候補」。研究者が採用すると、比較や図に使われる |
| 登録票 | ワークスペースごとに、どの視野のどの解析版を採用しているかを記録する表。コードでは `workspace_selections`、selection |
| 解析案 | AI が返す、解析の設定の提案。決まった形の JSON。コードでは proposal |
| ランタイム | 画面の状態と API の呼び出しをまとめる、ブラウザ側のモジュール |

### 2.2 Issue に合わせて改める、以前の決定

Issue の合格条件は、以前の 2 つの決定と両立しない。この文書は Issue に合わせる。オーナーから意見を求められたので、理由を添える。オーナーが別の判断をしたら、W3・W6・W8 を書き直す。

**同じ内容の画像を、別の視野として登録する（要件 I12、2026-10-06）**

改めるべきである。画素まで完全に同じ 2 枚が、別々に撮った画像であることはまずない。顕微鏡の画像にはノイズが乗るからである。内容が一致したら、それはコピーと考えてよい。いまの動作ではコピーを選ぶだけで視野が 1 つ増え、研究者はその数を観測数として読んでしまう。警告は「取込 2件」を開かないと見えない。

これからは、同じ内容の画像を 1 つにまとめる。研究者が「別の撮影として追加」を選んだときだけ別の視野にし、その選択を記録する。

**AI の解析案を、自動で設定に入れて試しに実行する（要件 L02、2026-10-06）**

依頼の種類で動作を分けるべきである。「核を数えて」と頼んだ人にとって、自動の試行は良い体験なので残す。結果がすぐ見え、採用するかどうかは研究者が決められる。

困るのは、質問や設定の変更にも同じ動作をする点である。答えを読みたいだけの人の設定を書き換え、解析を走らせてしまう。しかも、設定が検証を通らないと、AI が書いた文章まで捨てている。Issue の「質問しただけで形式エラー」は、ここから起きている。

これからは、質問には文章で答えるだけにする。設定の変更を頼まれたら設定だけを変える。実行を頼まれたときだけ解析を走らせる。

## 4. 目指す動作

どの作業も、次の原則を守る。迷ったときはここに戻る。

1. **1 枚の問題は、その 1 枚だけの問題にとどめる。** 読めない画像や名前の重なりがあっても、ほかの画像は登録され、指定した群に入り、測定と比較ができる。
2. **渡されたファイルは、必ず一覧に出る。** 黙って飛ばさない。置き換えない。消さない。受け取った数は、画像・マスクの候補・対象外・読み取れない、の内訳の合計と一致する。
3. **登録できなかった理由は、アプリが記録する。** ファイル名、どの段階で失敗したか、理由を保存し、開き直しても同じ名前で見せる。研究者に理由を書かせない。
4. **同じ内容の画像は、1 つの視野にする。** 研究者が別の撮影だと記録したときだけ分ける。
5. **AI の文章は、いつでも読める。** 設定が検証を通らなくても、文章の回答は表示する。検証が止めるのは、設定の適用だけである。
6. **AI は、頼まれたことだけをする。** 質問には答える。設定の変更を頼まれたら設定を変える。実行を頼まれたら実行する。
7. **会話は、作業と視野に結び付く。** 別のワークスペースに現れない。開き直すと戻る。戻すときに AI を呼び直さない。
8. **押したら、その場所で何かが変わる。** 受け付けた、進んでいる、終わった、断った、のどれかを必ず見せる。
9. **止まったら、理由を PC の中に残す。** サービス、更新、接続が止まったときの段階と理由を記録する。記録に研究データ（ファイル名、指示の文、画素）を入れない。

科学の規則は変えない。原画像の画素値を変えない。測定値と統計は `packages/analysis` と API の共通実装だけが作る。ファイル名やフォルダーから、群・実験回・染色を勝手に確定しない（案を出して研究者が確かめるのは構わない）。失敗した画像を、記録を残さずに除外しない。

## 5. 複数の作業が共有する設計

ここに書いた形は、複数の作業が使う。変えたいときは、同じ PR でこの節も直す。

### 5.1 受け取りの記録

研究者が渡したファイルを、1 つ残らず API の新しい表 `intake_items` に記録する。1 ファイルが 1 行になる。

いまは、画像を送る前に登録票へ「視野のない仮の行」を作っている。この仮の行には名前も理由も入らない。新しい表ができたら、仮の行は作らない。

| 列 | 内容 |
|---|---|
| `id` | UUID。画像を登録するときの `client_upload_id` にも使う。同じ `id` で送り直しても、視野は 1 つしかできない |
| `workspace_id` | ワークスペース |
| `batch_id` | 1 回の選択または 1 回のドロップ。「直前の追加を取り消す」の単位になる |
| `name` | 選んだフォルダーから見た相対パス。255 文字まで |
| `bytes`、`sha256` | 大きさと、内容のハッシュ |
| `role` | 役割。`image`（測る画像）、`label`（マスクの候補）、`other`（画像でないファイル）、`unreadable`（読み取れない）、`unknown`（まだ調べていない） |
| `code` | 読み取りに失敗した理由。API の読み取り処理が返すコード（例：`region_image_bit_depth_unsupported`） |
| `state` | 状態。`received`（受け取った。まだ視野になっていない）、`registered`（視野になった）、`withdrawn`（研究者が取りやめた）、`interrupted`（送信が途中で切れた） |
| `field_id`、`channel_id` | 視野になったときの、視野とチャンネル |
| `duplicate_of`、`separate` | 同じ内容の先行するファイルの `id`。研究者が「別の撮影として追加」を選んだら `separate` を真にする |
| `target` | 研究者が指定した追加先。`{run_id, group_id, sample}`。指定がなければ null |
| `stored`、`shape`、`dtype` | W5 で加える列。API がファイルの中身を保存したかどうかと、読み取った寸法と型 |

役割の決め方は 2 つだけにする。拡張子が TIFF でなければ `other`。TIFF なら、API の読み取り処理（`read_tiff` など）の結果で `image`・`label`・`unreadable` に分ける。ブラウザ側に別の判定を作らない。

この表は 2 段階で作る。W2 は表と記録だけを入れ、画像の中身はいままでどおりブラウザから登録の API へ送る。W5 は、受け取った時点で中身を API に保存し、縮小画像と「確定」の API を足す。同じ表を使い続ける。

ファイル名は研究データである。保存するのは PC の中のデータベースだけで、ログや診断には書かない。AI に送る範囲も変えない。

### 5.2 取り込みの結果

ランタイムの `importFiles` は、いまは「追加した視野の ID の配列」を返すか、例外を投げる。W1 で、戻り値を次の形に変える。

```ts
interface IntakeOutcome {
  registered: Array<{fieldId: string; names: string[]}>;              // 視野になった
  rejected:   Array<{item: string; names: string[]; code: string}>;   // API が読めずに断った
  held:       Array<{names: string[]; reason: "duplicate_channel" | "duplicate_content"}>; // 研究者の判断を待つ。まだ送っていない
  skipped:    Array<{name: string}>;                                  // 画像でないファイル
}
```

1 枚ずつの失敗では例外を投げない。例外を投げるのは、作業全体が続けられないときだけである（API から応答がない、セッションが切れた、ワークスペースが別の画面で変わった、容量の上限に達した）。そのときの例外 `IntakeInterrupted` は、そこまでの `IntakeOutcome` を持つ。呼び出した側は、例外でも、登録できた視野を処理できる。

### 5.3 会話の記録

AI とのやり取りを、API の新しい表 `assistant_messages` に保存する。研究者の発言 1 つが 1 行になる。

いまある表 `proposal_drafts` は、同じ依頼に同じ解析案を返すためのキャッシュで、指示の文を持たない。会話の記録とは分ける。同じ質問を 2 回送れば、発言は 2 行になる。

| 列 | 内容 |
|---|---|
| `id`、`workspace_id`、`created` | 発言 |
| `field_id` | 送ったときに開いていた視野 |
| `text` | 研究者が書いた文。2,000 文字まで |
| `state` | `pending`（送信中）、`answered`（回答あり）、`failed`（失敗） |
| `reply` | AI の文章の回答 |
| `applicable`、`reasons` | 解析案の設定を適用できるかどうか。できないときは、その理由のコード |
| `draft_id` | 適用できる解析案。`proposal_drafts` の行を指す |
| `effect` | この発言でアプリが行ったこと。`none`（何もしない）、`settings`（設定を変えた）、`run`（実行した） |

### 5.4 画面に出す状態の言葉

状態の表示は、次の言葉にそろえる。新しい言葉を作らない。

| 何の状態か | 言葉 |
|---|---|
| 受け取ったファイル | 読み込み中、追加待ち、登録済み、要確認、マスクの候補、対象外、読み取れない |
| 視野の解析 | 準備中、待機、検出中、候補を確認、保存済み |
| AI への発言 | 送信中、回答、失敗、設定を適用、実行 |
| 接続 | 接続中、再接続中、停止 |

画面の文言は、[開発の原則](../../development-principles.md#画面と文章)の規則に従う。ボタンと見出しは短い語にする。状態は「項目：値」で書く。説明の文を足して画面を埋めない。

5. 選んだ結果を必ず 1 行で見せる。フォルダーが空だった、画像が 1 つもなかった、の 2 つを区別する。ファイル選択を取り消したとき（`input` の `cancel` イベント）は、直前の選択をそのまま残す。

### W2 登録できなかった画像を記録し、比較を止めない

**いま起きていること**

- 正常な 4 枚と壊れた 1 枚を入れると、赤い帯に「比較の前に、理由を付けて除外してください」と出る。理由の欄にはアプリが文を入れていて、研究者は「除外」を押すよう求められる。
- 除外せずにページを開き直すと、壊れたファイルは「名称不明」になり、理由の欄は空になる。空のままでは「除外」を押せない。
- 全部の視野を測定しても、この行が 1 つ残っていると、群間比較は 409 `workspace_selection_incomplete` で計算されない。
- 壊れたファイルを直して入れ直すと、新しい行が増えるだけで、古い行は残る。

**原因**

画像を送る前に、登録票へ「視野のない仮の行」を作っている（API の呼び出し 236〜239 行）。この行が持つのは `id, field_id, revision_id, exclusion_reason` の 4 つだけである。ファイル名と失敗の理由は、ランタイムのメモリー（`failedImports`）にしかないので、開き直すと消える。

群間比較の API は、視野も理由もない行が 1 つでもあると計算を断る（`region_cohorts.py` の 90〜93 行）。[§2.1](#21-オーナーが決めたこと) のとおり、この規則は取り除く。

**直し方**

1. API に表 `intake_items`（[§5.1](#51-受け取りの記録)）と、次の経路を加える。
   - `POST /v1/workspaces/{wid}/intake-items`：ファイルの記録をまとめて作る。
   - `GET /v1/workspaces/{wid}/intake-items`：一覧を返す。
   - `PATCH /v1/workspaces/{wid}/intake-items/{id}`：取りやめ、追加先の変更、「別の撮影」の記録。
2. 画面は、画像を送る前に記録を作る。名前、大きさ、ハッシュ、`batch_id`、追加先を入れる。その `id` を `client_upload_id` に使う。画像でないファイルも、`role` を `other` にして記録する（中身は送らない）。
3. 画像を登録する API（`POST …/region-fields` と `…/region-fields/ome`）は、結果を記録に書く。成功なら `registered` と `field_id`。読み取りの失敗（422）なら `role` と `code`。視野の保存と同じトランザクションで書く。
4. `region_cohorts.py` の 90〜93 行の検査を消す。代わりに、比較の設定へ「登録できなかった画像」の数を、群・実験回ごと、理由ごとに入れる。この数を、結果の「n の内訳」、Methods、書き出しに出す。測定値と統計の計算は変えない。
5. ある群や実験回に有効な値が 1 つもないときは、いまある検査（`region_comparison_unit_without_values` など）がその比較を止める。この検査は残す。
6. 下端の「取込」の一覧を、`GET …/intake-items` から描く。読み取れない行には、名前、理由、「差し替え」「追加をやめる」を出す。次のものは消す。
   - 除外の理由の入力欄と「まとめて除外」（`UnfinishedImports.tsx`）
   - 統計の画面の「登録できなかった画像：n 件。比較の前に…」の行（画面本体 547 行）
   - ランタイムの `failedImports`、`unfinishedImports`、`excludeImports`
7. 「差し替え」は、同じ記録の `id` で画像を送り直す。視野ができたら記録は `registered` になり、指定してあった群に入る。記録も視野も増えない。
8. 古いワークスペースに残っている「視野のない仮の行」は、読むだけにする。一覧に「以前の取り込みの記録（名前なし）」として出し、何も止めない。新しくは作らない。

研究者が自分の判断で視野を外す操作（視野を「対象外」にして理由を書く）は、いままでどおり残す。これは研究上の除外で、読み取りの失敗とは別のものである。

**完成の条件**

- 正常な 4 枚と壊れた 1 枚を入れると、2 視野がすぐ使える。理由の入力も除外も求められない。
- ページを開き直しても、アプリを起動し直しても、壊れたファイルが元の名前と理由で一覧に出る。「名称不明」は出ない。
- 壊れた 1 枚だけを差し替えると、同じ行が「登録済み」になる。視野と群の割付は重複しない。
- 全部の視野が測定済みで、読み取れない画像が 1 件残っていても、群間比較が計算される。結果に、群ごとの有効な視野の数と、登録できなかった画像の数と理由が出る。
- 必要な群が空のときは、その比較だけが止まる。

**試験**

### W3 AI との会話を保存し、失敗の理由を見せる

**いま起きていること**

- 1 視野（DRAQ と GFP）を登録して、「この画像のチャンネル名を教えてください。まだ測定を実行せず、どれを核染色に使うか確認したいです」と送る。画面の上に「AI の解析案が、このアプリで扱える形式ではありませんでした。再送の前に設定を確認してください」と出る。会話の欄は「下の入力欄から解析を指示します」のまま。送った文は入力欄に残る。
- 新しいワークスペースを開いて別の画像を選んでも、入力欄と会話の欄に前の文が残る。
- 前日に回答をもらったワークスペースを開き直すと、回答が出ない。
- 視野が 1 つ以上あると、入力欄が空でも送信ボタンを押せる。

**原因**

- 画面は、研究者が書いた文をすべて「解析案を作る依頼」として API に送る。質問のための経路はない。
- API は、AI が返した解析案の設定を検証する。通らないと 502 `proposal_rejected` を返し、理由のコードの配列 `reasons` を付ける。このとき、解析案に入っている AI の文章（`rationale`）も一緒に捨てる。
- 画面は、エラーからコードだけを取り出し、`reasons` を読まない（`api.ts` 22〜26 行）。
- 表 `proposal_drafts` は、指示の文も理由も持たない。保存した解析案を読み出す API もない。画面が持つ解析案はメモリーの中だけなので、開き直すと消える。
- 入力欄の文字列 `instruction` は、送っても、新しいワークスペースを作っても消さない。会話の欄の「研究者の発言」は、この入力欄の文字列をそのまま描いている。
- 解析案が返ると、ランタイムはすぐに設定へ適用し、選んでいる視野でプレビューを実行する。

今回の質問が、51 種類ある検証のどれで落ちたのかは分からない。理由が保存されていないからである。この作業が終われば、同じことが起きたときに理由が残る。

**直し方**

1. API に表 `assistant_messages`（[§5.3](#53-会話の記録)）を足す。`POST …/proposal-drafts` は、受け付けた時点で発言を保存し、結果が出たら書き足す。`GET /v1/workspaces/{wid}/assistant-messages` で一覧を返す。
2. 設定が検証を通らなくても、AI の文章は返す。解析案から `rationale` と `missing_information` を取り出せて、文章の検査（URL、コード、マクロを含まない。`FORBIDDEN_TEXT`）を通れば、200 で `reply`、`applicable: false`、`reasons` を返す。文章を取り出せないときだけ、いまの 502 を返す。どちらの場合も、理由のコードを発言の行に保存する。
3. `api.ts` は、`detail.reasons` を `ApiError.reasons` に入れる。
4. ランタイムに発言の一覧を持たせる。ワークスペースを開いたときに、`GET` で読み込む。送信したら入力欄を空にする。新しいワークスペースを作ったら、一覧と入力欄を空にする。会話の欄は、この一覧から描く。

6. 返ってきた解析案を、自動で適用しない。適用できる解析案には、発言の下に「設定を適用」と「適用して試行」を出す。研究者が押すまで、設定を変えず、解析も走らせない。W8 が入ると、実行を頼んだ発言では押さなくても進む。

9. 公開デモは、記録した操作を再生して動く。デモの動作は変えない。記録を作り直す必要が出たら、作業を止めてオーナーに確かめる。

### W5 ファイルを API で受け取る

**いま起きていること**

- 画像を選んでも、登録するまで縮小画像が出ない。何を選んだのかを目で確かめられない。
- 原画像 4 枚、マスク 1 枚、説明の TXT 1 件を選ぶと「受け取った画像：6 件」と出る。マスクは「登録できなかった画像」になり、TXT は何も表示されずに消える。
- 同じ画像のコピーを一緒に選ぶと、視野が 2 から 3 に増える（対照試験 A）。

**原因**

選んだファイルは、登録するまでブラウザの中にしかない。ブラウザには TIFF を読む処理がないので、縮小画像を作れず、マスクかどうかも分からない。件数は、選んだファイルの総数をそのまま出している。拡張子が TIFF でないファイルは、ランタイムが何も言わずに飛ばす（472 行の `continue`）。

同じ名前のファイルが 2 つあると、ランタイムは 2 つ目に別のフォルダー名を付ける（476〜477 行）。視野を見分けるキーにはフォルダー名が入るので、2 つ目は別の視野になる。内容のハッシュは計算しているが、警告を出すだけである。

**直し方**

1. `POST /v1/workspaces/{wid}/intake-items/{id}/content` を足す。1 つのファイルの中身を受け取り、API の読み取り処理（`read_tiff`、OME の読み取り）で役割、理由、寸法、型、OME のチャンネル名を決めて保存する。256 MiB の上限は、ここで確かめる。共有の開発環境では、登録済みの公開画像だけを受け付ける制限（`CYTELLECT_UPLOAD_ALLOWLIST`）も、ここでかける。
2. `GET …/intake-items/{id}/preview` を足す。表示用の縮小画像を返す。原画像の画素は変えない。
3. `POST …/intake-items/commit` を足す。視野の組み合わせ（どの記録をどのチャンネルにするか）と追加先を受け取り、保存してある中身から視野を作る。ブラウザから中身を送り直さない。結果は、記録ごとに返す（[§5.2](#52-取り込みの結果) と同じ形）。
4. 中身を受け取ったら、同じワークスペースのほかの記録と、登録済みの視野の入力（`image_info.inputs` のハッシュ）に照らす。同じ内容があれば `duplicate_of` に書く。
5. 受け取った中身は、ワークスペースの容量に数える。保存期限と削除は、視野の入力と同じにする。取りやめた記録の中身と、視野になった後で不要になった重複は消す。

**完成の条件**

- BBBC007 の原画像 4 枚、32-bit のマスク 1 枚、TXT 1 件を受け取ると、`image` が 4、`label` が 1、`other` が 1 になる。合計は受け取った 6 件と一致する。
- 受け取った後でページを開き直しても、一覧と縮小画像が残る。
- 「確定」は、中身を送り直さずに視野を作る。同じ確定をもう一度呼んでも、視野は増えない。
- 同じ内容の 2 つ目のファイルに、`duplicate_of` が付く。

**試験**　API：役割と理由（公開画像と、試験の中で作る破損した画像）、容量、削除、確定の繰り返し、同じ内容の検出。

### W7 群と実験回に割り付ける

**いま起きていること**

### W8 AI への依頼を、質問・設定・実行に分ける

**いま起きていること**

### W9 進捗を視野ごとに出す

**いま起きていること**

- 設定を変えた直後は、ボタンは「測定」のまま、視野は「未測定」のままで、何も動いていないように見える。
- 2 視野の核小体を測ると、進捗が「0/4：検出・測定中」と出る。
- 候補ができても、採用するまで、一覧は「未測定」のままである。
- 途中で通信が切れると `Failed to fetch` と出て、どの視野まで終わったのかが分からない。

**原因**

- 進捗は、ヘッダーの 1 行（`operation`）だけに出している。分母は視野の数ではなく、実行のステップの数である。ステップは「視野 × 領域の段数」で作るので、2 視野の核小体では、核と核小体の 4 つになる。
- 一覧の「未測定」は、採用済みの結果があるかどうかだけを見ている。候補を見ていない。
- 設定を変えてからプレビューが始まるまで、650 ミリ秒待つ。その間は何も出さない。
- 進捗を取りに行く処理は、通信の誤りが 1 回あるとすぐ失敗にする。

**直し方**

1. 実行のステップ（`field_id`、`target`、`state`）から、視野ごとの状態を作る。準備中、待機、検出中（どの領域か）、候補を確認、保存済み。これを一覧の各視野に出す。候補がある視野は「未測定」ではなく「候補を確認」にする。
2. ヘッダーの進捗は、視野を単位にする。例：「視野 1/2：核小体を検出中」。
3. 設定を変えた直後と、「測定」を押した直後から、その視野に「準備中」を出す。
4. 進捗を取りに行く途中で通信が失敗しても、すぐには失敗にしない。解析は API の側で続いている。間隔を空けて取り直す。戻らなければ、W10 の案内に渡す。そのとき、保存済みの視野と、やり直す視野を示す。同じ依頼は、いまある `request_id` の仕組みで二重に起動しない。
5. 1 つの視野が失敗しても、残りの視野は続ける。失敗した視野に「再試行」を出す。

**完成の条件**

- 2 視野で、設定の変更、プレビュー、全体の測定、採用のどの時点でも、各視野の状態と次にする操作が分かる。分母は 2 である。
- 候補ができた視野は「候補を確認」、採用した視野は「保存済み」と出る。一覧と画像の表示が食い違わない。
- 途中で通信を切っても、保存済みの視野とやり直す視野が分かる。同じ処理が二重に走らない。

**試験**　単体：ステップから視野の状態を作る処理、取り直し、二重に起動しないこと。画面：2 視野の核小体の測定。`cytellect-screen-check`。

### W10 接続が切れたときの案内と復帰

**いま起きていること**

- 画像を登録している途中で `Failed to fetch` と出て、視野は 0 のまま。調べると、ローカルの API（8765 番）が止まっていた。止まった理由は分からない。
- ランチャーを起動し直した後、前から開いていたタブで操作すると、「作業画面の接続が切れました。ブラウザでこのページを再読み込みしてください」と出る。
- 赤い帯の「再読み込み」ボタンは、保存した状態を読み直すだけで、送りかけの画像は送り直さない。

**原因**

- 画面は、API から応答がない失敗を、ブラウザのメッセージのまま出している（ランタイム 48 行の `message`）。
- セッションが切れた（401 `session_required`）とき、画面はページの再読み込みを求める。セッションを作り直す API（`POST /v1/local/session`）はあり、更新の追跡は使っているが、ほかの呼び出しは使っていない。
- ローカルのサービスが止まる経路は 5 つある。ランチャーを閉じる。更新で新しい版に切り替わる。計算ワーカーが止まる。ランチャーの親プロセスが消える。予期しない例外。どの経路も、理由を記録しない。
- 計算ワーカーは、止まると 2 回まで自動で起動し直す。3 回目に止まると、サービス全体を止める。この回数は、ランチャーを起動してからの通算で数えていて、元に戻らない。長く使っていると、離れた 3 回の停止でサービスが止まる。

最後の点は、コードを読んで見つけた。Issue のときの停止がこの経路だったとは、確かめていない。どの経路でも理由が残るようにして、次に起きたときに分かるようにする。

**直し方**

1. 失敗を 3 種類に分けて、それぞれの案内を出す。

   | 失敗 | 見分け方 | 画面 |
   |---|---|---|
   | 応答がない | `fetch` が失敗する | 「ローカルのサービスに接続できません」と「再接続」を出す。間隔を空けて、自動でも確かめる。ランチャーの開き方を 1 行で示す |
   | セッションが切れた | 401 `session_required` | `POST /v1/local/session` でセッションを作り直し、同じ呼び出しを 1 回やり直す |
   | 開き方が違う | 403 `local_origin_required` | デスクトップの「Cytellect」から開くよう案内する |

2. 接続が戻ったら、受け取りの記録と視野を照らし合わせる。視野になっている記録は「登録済み」にする。送信が途中で切れた記録は `interrupted` として残す。中身が API にあれば（W5）、そのまま続ける。なければ、ファイル名を示して、選び直してもらう。画像の登録は同じ `id` で送り直しても視野が増えないので、安全にやり直せる。
3. サービスが止まる 5 つの経路すべてで、理由のコードと時刻を、PC のデータフォルダーの記録に書く。次に起動したとき、前回が異常な停止だったら、1 行で知らせる。
4. 計算ワーカーが止まっても、サービス全体は止めない。起動し直した回数は、ワーカーがしばらく正常に動いたら 0 に戻す。どうしても起動できないときは、API は応答を続け、解析の受付だけを `local_worker_stopped` で断る。画面には、理由と「ワーカーを再起動」を出す。

**完成の条件**

- 応答がない、セッションが切れた、開き方が違う、の 3 つで、案内と直し方がそれぞれ違い、正しい。
- 画像を登録している途中でサービスを止め、起動し直す。登録済みの視野は重複せず、残りの画像を続けて登録できる。選んだ一覧は消えない。
- 止まった理由が記録に残り、次の起動で分かる。記録に、ファイル名や指示の文は入っていない。

**試験**

### W11 更新の案内

**いま起きていること**

- 新しい版の案内が、空の画面にも、取り込みの途中にも、AI のエラーの上にも出続ける。閉じる方法がない。
- 研究者から「押しても反応がない」という報告がある。
- 以前の更新の失敗が `update_install_failed` と記録されているが、何が起きたのかは分からない。

**原因**

- 通常の案内（「更新があります」）に付いているのは、「更新」と「変更内容」だけである。「閉じる」が付くのは、失敗と完了の表示だけ（`CloudAccount.tsx` の 256 行）。
- ボタンを押した後の分かれ道は 5 つある。始まる。別のタブで進行中。解析中なので断る。新しい版がない。この PC では更新できない。このうち「新しい版がない」は、黙って状態を読み直すだけである。「更新できない」は、案内を黙って消す（241 行）。押した人には、何も起きなかったように見える。
- インストーラーの起動に失敗しても、時間切れになっても、`run_installer` は同じ -1 を返す。インストーラーの出力は捨てている。0 以外で終わった場合は、すべて `update_install_failed` になる（`app_update.py` の 269〜283 行、472〜475 行）。

「押しても反応がない」が、上のどの分かれ道だったのかは分からない。どの分かれ道でも結果が見えるようにする。

**直し方**

1. 通常の案内に「後で」を足す。押したら、アプリを次に起動するまで案内を出さない。
2. ボタンを押した直後から、同じ場所に段階を出す。受け付けた、ダウンロード中、インストール中、再起動中、完了。
3. 何も見えなかった 2 つの分かれ道に、1 行の結果を出す。「新しい版はありません」。「この PC ではアプリの中から更新できません」と、代わりの方法。
4. 解析中に押されたら、「解析が終わってから更新してください」と出し、解析は止めない。これはいまの動作である。二重に押されたときと、別のタブで進行中のときは、進行中の更新の段階を出す。
5. 失敗の段階を記録する。`run_installer` が、段階（起動、時間切れ、終了）と終了コードを返すようにする。失敗のコードを 3 つに分ける。`update_installer_launch_failed`、`update_installer_timeout`、`update_install_failed`（終了コードつき）。状態の記録に `stage` と `exit_code` を残す。インストーラーのログは、PC の更新フォルダーに残す。外には送らない。
6. Microsoft Store から入れた版は、Store が更新する。この版で案内がどう出るかを、コードと試験で確かめる。出すなら、Store への案内だけにする。
7. ボタンの言葉をそろえる。Issue は「アップデート」と書いているが、`main` のコードは「更新」である（`cloud-account.ts` の 314 行）。配布版 0.1.0-local.26 の表示を確かめ、1 つの言葉にする。

**完成の条件**

### W12 Windows の実機で確かめる

**なぜ必要か**

Issue は、Windows のインストール版を Edge で操作して見つけた問題である。開発環境の試験が通っても、実機で直ったとは言えない。配布の候補ができたら、Issue と同じ環境で確かめる。

**手順**

配布の候補をインストールし、Issue の「入力の用意と再現の約束」にある公開画像を使って、次を順に行う。画面の写真と時刻を記録する。

1. Issue の受け入れテスト 6 件（[§3.3](#33-issue-の優先して直したい操作と受け入れテスト)）。
2. フォルダー。Edge のふつうのフォルダー選択で、原画像のサブフォルダー（4 件）と親フォルダー（10 件）を、選ぶ、取り消す、確定する。同じ 2 つを、ドラッグ＆ドロップでも試す。
3. 接続。画像を登録している途中でランチャーを閉じ、開き直す。前から開いていたタブで操作する。
4. 更新。W11 の 7 つの場面。
5. アプリを起動し直して、群の中身、登録できなかった画像の名前、AI との会話が戻ることを確かめる。

**完成の条件**

受入の記録（`docs/local-release-<版>.md`）に、合格、失敗、未実施を分けて書く。

初めて使う研究者に試してもらう評価（迷って戻った箇所と、手助けした回数を数える）は、この作業とは別に、未完了の項目として残す。

**前提**　配布する範囲の作業が終わっている。配布には、オーナーの許可が要る。

- **最初に着手するのは W1 と W3 である。** どちらも前提の作業がなく、Issue が最優先とした症状を止める。W1 の後に W2 を行う。

- 画面本体のファイルは、W1、W3、W6、W9 が触る。同時に進めるときは担当を分け、W1、W3、W9、W6 の順に `main` へ入れる。W3 は AI のパネルを、W6 は取り込みを、それぞれ別の部品に切り出す。画面本体の同じ行を触る量が減る。
