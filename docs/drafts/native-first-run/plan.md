## 4. 不変条件

実装と試験は、次を守る。作業単位の完了条件は、これを具体化したもの。

- **I-1**　取り込みは項目ごとに結果を持つ。1 つの項目の結果が、ほかの項目の登録・表示・割付を止めない。
- **I-2**　研究者が渡したファイルは、役割と状態を付けて必ず一覧に出る。黙って飛ばす・置き換える・消すことをしない。
- **I-3**　受け取った件数は、役割ごとの内訳の合計と一致する。
- **I-4**　登録できなかった入力は、名前・段階・理由コードをアプリが保存する。再起動後も同じ名前で見える。研究者に理由を書かせない。
- **I-5**　登録できなかった入力は、ほかの視野の測定・比較・AI を止めない。比較は群ごとの有効数と欠測を示し、必要な群や実験回が空のときだけ、その比較を保留する。
- **I-6**　同じ内容のファイルは、研究者が別の撮影と記録しない限り、1 つの視野になる。
- **I-7**　AI の文章の回答は、設定の検証の結果にかかわらず表示する。検証が止めるのは設定の適用だけ。
- **I-8**　AI は、研究者が実行を頼んだときだけ解析を走らせ、設定の変更を頼んだときだけ設定を変える。
- **I-9**　発言・応答・失敗は、作業（ワークスペース）と視野に結び付けて保存し、別の作業に現れない。再表示で作り直さない。
- **I-10**　押した操作には、その場所に受付・進行・結果のどれかが出る。何も変わらない分岐を作らない。
- **I-11**　サービス・更新・接続が止まったら、段階と理由コードを PC の中に記録する。記録に研究データ（ファイル名、指示の原文、画素）を入れない。

科学の規則は変えない：原画像の画素値を変えない。測定値と統計は共通実装だけが作る。ファイル名やフォルダーから群・実験回・染色を**確定**しない（E-04、I11、U02。案を出して研究者が確かめるのは確定ではない）。失敗した視野を黙って除外しない（I-4・I-5 は記録して見せる）。

## 5. 共通の設計

### 5.1 受け取り

研究者が渡したすべてのファイルの記録を、API の表 `intake_items` に 1 行ずつ持つ。登録票（`workspace_selections`）の「視野のない仮の票」は作らない。

| 列 | 内容 |
|---|---|
| `id` | UUID。画像の登録では `client_upload_id` に使う（同じ ID の再送は冪等。I11） |
| `workspace_id`、`batch_id` | 作業と、1 回の選択・ドロップ（取り消しの単位） |
| `name` | 選んだフォルダーからの相対パス。255 字まで |
| `bytes`、`sha256` | 大きさと内容のハッシュ |
| `role` | `image`（測定する画像）・`label`（マスクの候補）・`other`（対象外）・`unreadable`（読み取れない）・`unknown`（未判定） |
| `code` | 共通の読み取り処理が返した理由コード（例：`region_image_bit_depth_unsupported`）。なければ null |
| `state` | `received`（受け取り済み・未登録）・`registered`・`withdrawn`（研究者がやめた）・`interrupted`（送信が終わらなかった） |
| `field_id`、`channel_id` | 登録先の視野とチャンネル |
| `duplicate_of` | 同じ内容の先行する項目の ID。`separate`（真偽）は「別の撮影として追加」の記録 |
| `target` | 研究者が指定した追加先 `{run_id, group_id, sample}`。なければ null |
| `stored`、`shape`、`dtype` | W5 で加える。バイトを API に保存したか、読み取った寸法と型 |

### 5.2 取り込みの結果

```ts
interface IntakeOutcome {
  registered: Array<{fieldId: string; names: string[]}>;
  rejected:   Array<{item: string; names: string[]; code: string}>;  // API が読み取りで拒否
```

### W10 接続：区別・再接続・停止の理由

- **種類**　fix(web, api)。依存：W1。
- **目的**　サービスの停止・セッション切れ・開き方の誤りを区別し、選択と登録の結果を失わずに戻る。サービスが止まった理由を残す（I-10、I-11）。
- **原因**　`RT:48` の `message()` は、応答のない失敗（`Failed to fetch`）をそのまま出す。401 では再接続せず、ページの再読み込みを求める（`api.ts:351`）。「再読み込み」ボタンは保存状態を読み直すだけ（`RT:385`）。サービスの停止は G10。
- **触るファイル**　Web：`api.ts`（再接続とやり直し）、`RT`（`message`、`reload`、照合）、`CW:515`（案内）。API：`local.py`（停止の理由の記録、ワーカーの再起動の数え方、起動時の案内）。
- **手順**
  1. 失敗を 3 つに分ける。

     | 状況 | 見分け方 | 画面 |
     |---|---|---|
     | 応答がない | `fetch` の失敗 | 「ローカルのサービスに接続できません」と「再接続」。自動でも間隔を空けて確かめる。ランチャーの開き方を 1 行で示す |
     | セッション切れ（401 `session_required`） | 応答のコード | 再接続（`POST /v1/local/session`。更新の追跡は既に使っている：`cloud-account.ts:68`）を 1 回行い、同じ要求をやり直す |
     | 開き方の誤り（403 `local_origin_required`） | 応答のコード | デスクトップの「Cytellect」から開く案内 |

  2. 再接続の後、受け取りの記録（`intake_items`）と視野を照合する。登録済みは「登録済み」、送信が終わらなかった項目は `interrupted` として残し、バイトが API にあれば（W5）そのまま続け、なければ名前を示して選び直しを求める。画像の登録は同じ ID で冪等。
  3. 未送信・送信後に応答が消えた・再接続・401・403 を、試験で別々に通す。
  4. **停止の理由を記録する。** サービスが止まるすべての経路（ランチャーを閉じる、更新の切り替え、ワーカーの停止、ワーカーの起動失敗、親プロセスの消失、捕まえていない例外）で、理由コードと時刻を PC のデータフォルダーの記録に書く。次の起動で、前回が異常な停止なら 1 行で知らせる。
  5. **ワーカーの停止でサービス全体を止めない。** 再起動の回数は、正常に動いた時間の後で戻す（今は通算 3 回目で止まる）。再起動できないときは、API は応答を続け、解析の受付だけを `local_worker_stopped` で断る。画面は理由と「ワーカーを再起動」を出す。
- **完了条件**
  - 応答なし・401・403 で、案内と復旧の方法がそれぞれ違い、正しい。
  - 取り込みの途中でサービスを止めて起動し直すと、登録済みの視野が重複せず、残りの項目を続けられる。選んだ一覧が消えない。
  - 停止の理由が記録に残り、次の起動で分かる。記録に研究データがない。
- **試験**　単体：3 つの区別、やり直し、照合。API：停止の理由の記録、ワーカーの再起動の数え方（`tests/test_local*.py`）。Windows の CI（`windows-installer`）で、ワーカーを止めた後もサービスが応答することを確かめる。

- **レビュー**　`/code-review medium`、`/security-review`（セッション）。

  4. 失敗の段階を記録する。`run_installer` は段階（起動・タイムアウト・終了）と終了コードを返す。失敗コードを `update_installer_launch_failed`・`update_installer_timeout`・`update_install_failed`（終了コードつき）に分け、状態の記録に `stage` と `exit_code` を残す。インストーラーのログは PC の更新フォルダーに残し、外へ送らない。
  5. Microsoft Store の版は Store が更新する。この案内を出さないこと（または Store への案内だけを出すこと）を、コードと試験で確かめる。
  6. 画面の文言を確かめる：Issue は「アップデート」、`main` のコードは「更新」（`cloud-account.ts:314`）。配布版 .26 の表示と突き合わせ、1 つの語にそろえる。
- **完了条件**（Issue「次の追試と合格条件」）
  - 「後で」、解析中、二重クリック、別タブで進行中、起動の拒否、タイムアウト、0 以外の終了を、隔離した更新の試験で別々に通す。どの場合も、押したことが受け付けられたか・今の段階・次にすることが同じ場所に出る。
  - 失敗は段階と終了の理由を記録する。画像の選択と解析の作業を保つ。
- **試験**　単体：`updateNotice` と `UpdateBanner` の分岐、「後で」。API：`run_installer` の 3 つの失敗、状態の記録。Windows の CI（`packaging/windows/smoke.ps1`）の更新の試験に、失敗の段階を足す。
- **文書**　`docs/local.md`（更新の節）、`docs/install-windows.ja.md`、`docs/release-signing.md`。
- **レビュー**　`/code-review medium`、`/security-review`（更新）。

### W12 Windows の実機での受入

- **種類**　test（記録）。依存：W1〜W11 のうち配布する範囲。配布はオーナーの許可が要る。
- **目的**　Issue を起票したときと同じ環境（インストール版、Edge）で、Issue の受け入れテストを通す。開発環境の試験の合格を、実機の合格として報告しない。
- **手順**　配布候補をインストールし、Issue の「入力の用意と再現の約束」の入力（公開データセット）で、次を順に行い、画面と時刻を記録する。
  1. 受け入れテスト 1〜6（[§2.3](#23-優先して直したい操作と受け入れテスト)）。
  2. フォルダー：Edge の通常のピッカーで、原画像のサブフォルダー（4 件）と親フォルダー（10 件）を、選択・取り消し・確定。ドラッグ＆ドロップも同じ 2 つで。
  3. 接続：取り込みの途中でランチャーを閉じて開き直す。開いたままの古いタブから操作する。
  4. 更新：隔離した更新の試験（W11 の完了条件の 7 つ）。
  5. 再起動をはさんで、群の中身・登録できなかった項目の名前・会話が戻ることを照合する。
- **完了条件**　受入の記録（`docs/local-release-<版>.md`）に、合格・失敗・未実施を分けて書く。初見の研究者による評価（迷って戻った箇所と支援の回数）は、別の未完了の項目として追跡する。

## 7. 順序と並行

```text
段 1（画面を作り替えずに止める）   W1 → W2          W3          W9      W11
                                    └→ W10
段 2（画面の作り替え）             W4 → W5 → W6 → W7
段 3（AI）                         W3 → W8（W7 の後に割付の案）
受入                               W12
```

- 最初に着手するのは **W1 と W3**（依存がなく、最優先の症状を止める）。続けて W2。
- W1・W3・W9・W11 は互いに独立で、並行できる。ただし `CW` を触るもの（W1・W3・W6・W9）は、同時に進める場合に担当を分け、**W1 → W3 → W9 → W6 の順に取り込む**。W3 は AI のパネルを `AssistantPanel.tsx` に、W6 は取り込みを `IntakeList.tsx`・`EmptyStart.tsx` に切り出し、`CW` の同じ行を触る量を減らす。
- W3 と W8 は、同じ Windows 版の配布に入れることを目標にする。W8 の Worker のデプロイが遅れる場合、W3 だけでも配布できる（解析の依頼に「適用して試行」の 1 回のクリックが増えるが、質問で解析が走ることはなくなる）。
- 公開デモ（`/demo`）は画像の追加を受け付けない。W1・W2・W5〜W7 はデモの動作を変えない。W3・W8・W9 は共通の部品を変えるため、デモの記録に影響しないことを各 PR で確かめる。
- どの作業単位も、変更に当てはまるスキル（[CLAUDE.md](../../../CLAUDE.md#目的別のスキル)）を使い、`cytellect-verify` と、画面を変えたら `cytellect-screen-check` を実行してから `cytellect-pr` で PR を作る。
