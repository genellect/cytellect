## 4. 設計

守る不変条件を先に置く。

- **I-1**　取り込みは項目ごとに結果を持つ。1 つの項目の結果が、ほかの項目の登録・表示・割付を止めない。
- **I-2**　次に再送される集合は、画面の一覧に「未登録」と見えている項目と一致する。見えない再送待ちを持たない。
- **I-3**　受け取った件数は、役割ごとの内訳の合計と一致する。
- **I-4**　登録できなかった入力は消さない。名前・段階・理由コードを保存し、再起動後も同じ名前で見える。
- **I-5**　AI の応答は、研究者の依頼が実行でない限り、設定を変えず、解析を走らせない。
- **I-6**　発言・応答・失敗は作業（ワークスペース）と視野に結び付けて保存し、別の作業に現れない。

### 4.1 取り込みの結果を項目ごとに返す

対象：G1・G2、PR ①。

`importFiles` の戻り値を、項目ごとの結果に変える。

```ts
interface IntakeOutcome {
  registered: Array<{fieldId: string; names: string[]}>;
  rejected:   Array<{entry: string; names: string[]; code: string}>;   // API が 422 で拒否
  held:       Array<{names: string[]; reason: "duplicate_channel" | "duplicate_content"}>; // 判断待ち。未送信
  skipped:    Array<{name: string}>;                                    // 対象外の拡張子
}
```

- 項目ごとの拒否と競合では例外にしない。例外にするのは、続けられない失敗（接続断、セッション切れ、ワークスペースの変更）だけで、その例外もそこまでの結果を運ぶ。
- 呼び出し元（`addToExperiment`、`placePending`）は、結果がどちらでも `registered` を群に割り付ける。
- `duplicate_channel` は、競合した**視野だけ**を `held` にし、ほかの視野は登録する。`held` の項目は `added` から外して一覧に出し、研究者がどちらを使うかを選ぶ（I-2）。
- 項目ごとの結果は画面上部の赤い帯ではなく「取込」の一覧に出す。赤い帯と「再読み込み」は、作業全体が止まった失敗だけに使う。

### 4.2 登録票に取り込みの記録を持たせる

対象：G3、PR ②、判断 D1。

`WorkspaceSelectionEntry` に、省略できる `intake` を加える（古いクライアントは今までどおり）。

```text
intake: { names: [最大 4 件、各 255 字], state: "pending" | "rejected",
          code: 理由コード | null, target: {run_id, group_id, sample} | null, recorded: 時刻 }
```

- **名前と追加先**は、送信の前にクライアントが票に書く（今の `registerImport` と同じ時点）。
- **理由コード**は API が書く。`POST /v1/workspaces/{wid}/region-fields` が読み取りの誤りで 422 を返すとき、`client_upload_id` と同じ ID の票に `state: "rejected"` と `code` を同じトランザクションで記録する。研究者が打った文ではなく、共通の読み取り処理が出した理由だけが「技術的な失敗」になる。
- **差し替え**は、同じ票の ID を `client_upload_id` にして送る。視野ができると、今の `selection_at` が票と結び付ける（`workspace_selection.py:111-113`）。新しい票は増えない。
- **比較**（`region_cohorts.py:90-93`）は、`rejected` の票では止めない。比較の結果に「登録できなかった画像」を群・実験回ごとの件数と理由コードで残し、n の内訳・Methods・書き出しに出す。必要な群や実験回が空になる比較は、今の検査（`region_comparison_unit_without_values` など）が止める。
- 画面は「名称不明」を出さない。`rejected` の行は「名前：理由」と「差し替え」「追加をやめる」を持ち、除外の理由の入力欄は出さない。研究者が意図して外す視野は、今までどおり理由付きの除外（`excludeField`）を使う。

ファイル名は研究データで、保存先はこの PC のデータベースだけ（視野の表示名と同じ扱い）。ログ・診断・AI への送信範囲は変えない。`SECURITY.md` と `docs/security.md` の保存する項目に追記する。

### 4.3 役割と数え方

対象：G4、PR ⑤・⑥。

役割は 4 つ：**画像**（測定する）、**マスクの候補**、**対象外**（画像でないファイル）、**読み取れない**。

- 対象外は拡張子で決める（今の `isSupportedImage`）。
- 画像・マスクの候補・読み取れないは、API の共通の読み取り処理の結果で決める（`region_image_bit_depth_unsupported` はマスクの候補）。ブラウザに別の判定を持たない。
- 一覧の先頭に内訳を 1 行で出す：「受け取り 6：画像 4（2 視野）・マスクの候補 1・対象外 1」（I-3）。
- マスクの候補は、寸法が合う視野を横に示すだけにする。領域として使う操作（API の `labels` の経路）は、この計画の範囲に含めない。染色や生物学的な役割は推定しない。

### 4.4 視野の同一性

対象：G5、PR ⑤・⑥、判断 D3。

- 同じ取り込みの中で内容（SHA-256）が同じファイルは、1 つだけを使う。行に「同一内容：○○ と同じ」と出し、「別の撮影として追加」を選んだときだけ別の視野にする（その選択を票に残す）。
- 登録済みの視野の入力（API が持つ `image_info.inputs` のハッシュ）と同じファイルは「登録済み」と出し、視野を増やさない。
- 名前の競合（同じ視野・同じチャンネルに 2 枚）は、その行だけで解く。2 枚を名前と縮小画像で並べ、使う 1 枚を選ぶ。
- API は今までどおり、別の鍵での登録を別の視野として受け付ける（明示した場合の経路）。変わるのは画面の既定だけ。

- 選択は積み上がる。行ごとの「×」と、直前の追加の取り消しを持つ。
- 「追加」で登録し、最初の視野を「画像」で開く。AI の入力欄はそのまま使える。
- 1 画面・2 画面の選択は「実験」に残し、登録済みの視野を後から割り付ける（[§4.6](#46-群と実験回の割付)）。「実験デザインから始める」を選んだ人は、今の流れ（群のセルから追加）のまま進める。

**受け取りを API に置く（PR ⑤、推奨）**　選んだファイルを、視野にする前に API の「受け取り」に保存する。

| | A：ブラウザに置く（今の延長） | B：API に置く（推奨） |
|---|---|---|
| 登録前の縮小画像 | 出せない（ブラウザに TIFF の読み取りがない） | 共通の読み取り処理で作る |
| 再読み込み | 選んだファイルを失う（名前だけ残せる） | 残る |
| 役割の判定 | 送ってみるまで分からない | 受け取った時点で分かる |
| 後から選んだ同じ視野の別染色 | 別の視野になる | 追加の前に 1 視野にまとめられる |
| 完全な Web アプリ化 | 作り直しになる | そのまま使える |
| 追加の作業 | 小さい | 受け取りの表と API、容量・保存期限・削除、OpenAPI と型、`security.md` |

B の概要：`POST /v1/workspaces/{wid}/intake`（1 ファイルずつ。ハッシュ、寸法、ビット深度、役割、理由コード、縮小画像を返す）、`GET …/intake`（一覧）、`DELETE …/intake/{id}`、`POST …/intake/commit`（視野の組と追加先を受け取り、保存済みのバイトから視野を作る。再送しない）。受け取ったファイルはワークスペースの容量に数え、保存期限と削除は視野の入力と同じにする。共有の開発環境の登録済み画像の制限（`CYTELLECT_UPLOAD_ALLOWLIST`）は受け取りの時点でかける。[§4.2](#42-登録票に取り込みの記録を持たせる) の `intake` の形は受け取りの記録と同じにし、作り直さない。

**選ぶ前の見本**（D4）　「測る蛍光画像」「同じ視野の別染色」「輪郭のマスク」の縮小見本 3 枚を空の作業に置く案は、登録済みの公開画像とクレジットが要り、画面の要素も増える。案の画像で要否を決める。

### 4.6 群と実験回の割付

対象：PR ⑦。

- 「実験」に「未割り当ての視野」の表を置く。行は視野（縮小画像・名前）、列は実験回と群。複数の行を選んで一度に割り付けられる。
- フォルダー階層と名前から**案**を出す（例：`Rep1/未処理` → 実験回 Rep1・群 未処理）。今の `candidates`（`grouping.ts:231`）を広げ、決まった規則だけで作る。案は薄く表示し、「案を適用」を押すまで保存しない（E-04、I11、U02）。番号だけのチャンネル（C01）から染色を決めない。
- フォルダーの相対パスは、案を再読込後も出せるように視野の記録に保存する（今は表示名の最後の区切りだけ。`api-adapter.ts:62`）。
- 「未処理と ActD に分けて」のような指示での割付は、同じ表への案として AI の道具にする（[§4.7](#47-ai相談条件の変更実行) の段 c）。

### 4.7 AI：相談・条件の変更・実行

対象：G6、PR ③・⑧、判断 D5・D6。

**段 a：発言を作業に結び付ける（PR ③。プロトコルは変えない）**

- ランタイムに発言の一覧を持つ。1 件は `{id, 視野, 文, 状態（送信中・回答・失敗・適用済み）, 理由コード, 解析案}`。入力欄は送信で空にし、発言は一覧に出す。新しい作業では一覧を空にする（I-6）。
- `ApiError` に `reasons` を持たせ、`detail.reasons` を捨てない。失敗はその発言の下に出し、「設定を直せば通る理由」と「サービス側の誤り」を理由コードで分ける。再送はその発言のボタンにする（今の `retry_failed`）。
- `proposal_drafts` に `goal`・`field_id`・`reasons` を加え、`GET /v1/workspaces/{wid}/proposal-drafts` で一覧を返す。開き直したときは保存済みの発言と回答を出し、作り直さない。指示の原文はこの PC のデータベースにだけ保存する（D6）。
- 空欄の送信をやめる。画像だけからの解析案は、AI のパネルの「解析案を作る」ボタンにする（送る内容は今の空欄の送信と同じ）。

**段 b：相談と実行を分ける（PR ⑧、D5）**

- 解析案の契約に `intent`（`answer`・`settings`・`run`）と、自由な文の `answer` を加える（[見直し案 §2.1](../llm-assistant/plan.md#21-外す緩める品質を下げている)の「説明・質問・助言を自由な文章で返す欄」）。依頼の種類はモデルが宣言し、アプリは宣言に対して決まった動作だけをする。指示の文の語句で分岐しない。

| `intent` | アプリの動作 |
|---|---|
| `answer` | 文を出すだけ。設定を変えず、解析を走らせない。検証は、設定の変更を含まないことを確かめる |
| `settings` | 検証した設定を適用する（「AI による設定変更を戻す」は今のまま）。解析は走らせない |
| `run` | 設定を適用し、対象（選択視野・全視野）を発言に示して候補を作る。採用は研究者が行う（今と同じ） |

- **画像の事実**は AI を待たずに出す。選択した視野のチャンネル（名前と、その由来：ファイル名・OME・利用者）、寸法、ビット深度、核染色の指定の有無を、AI のパネルの先頭に「項目：値」で常に示す。AI が無効でも、Issue の質問（チャンネル名）の答えは画面にある。
- Worker のプロンプトと契約の版を上げる。配布済みの版は今の版のまま答える（今の版の切り替えと同じ）。Worker のデプロイ、有料の評価、Windows 版の配布は、それぞれオーナーの許可が要る。

**段 c：対話と道具**は[見直し案の段階 2](../llm-assistant/plan.md#5-進め方) のまま別の計画で進める。段 a の発言の一覧と保存は、段階 2 がそのまま使う。

### 4.8 視野ごとの進捗

対象：G7、PR ⑨。

- 実行のステップ（`field_id`・`target`・`state`）から、視野ごとの状態を作る：**待機・検出中・候補を確認・保存済み**。一覧の各視野に出し、採用前の候補があれば「未測定」ではなく「候補を確認」にする。
- ヘッダーの進捗は視野を単位にする（「視野 1/2：核小体を検出中」）。
- 設定を変えた直後から、その視野に「準備中」を出す（650 ms の待ちの間も）。
- 進捗の取得中の通信の誤りでは、すぐに失敗にしない。実行は API 側で続くため、間隔を空けて取得し直し、戻らなければ[接続の案内](#49-接続の区別と再接続)に渡す。同じ依頼は今の `request_id` で重複しない。

### 4.9 接続の区別と再接続

対象：PR ⑩。

| 状況 | 見分け方 | 画面 |
|---|---|---|
| 応答がない（サービスが止まった） | `fetch` の失敗 | 「ローカルのサービスに接続できません」と「再接続」。戻ったら保存状態を読み直す |
| セッション切れ（401 `session_required`） | 応答のコード | 再接続（`POST /v1/local/session`。更新の追跡は既に使っている：`cloud-account.ts:68`）を 1 回行い、同じ要求をやり直す。画像の登録は同じ `client_upload_id` で冪等 |
| 開き方の誤り（403 `local_origin_required`） | 応答のコード | デスクトップの「Cytellect」から開く案内（今の文） |

再接続の後は、登録票と視野を照合し、登録済みの項目を「登録済み」に、残りを「未登録」にする（I-2）。

### 4.10 更新案内

対象：G8、PR ⑪、判断 D7。

- 通常の案内に「後で」を加える。押したら、その起動の間は出さない。
- 押した直後から完了・失敗までを同じ場所に出す（今の「更新中…」を、押した時点から出す）。解析中は「解析が終わってから更新してください」を出す（今の文）。
- 失敗の段階を記録する。`run_installer` は段階（起動・タイムアウト・終了）と終了コードを返し、状態ファイルに `stage` と `exit_code` を残す。インストーラーのログはこの PC の更新フォルダーに残し、外へ送らない。失敗コードを起動失敗・タイムアウト・0 以外の終了で分ける。
- Microsoft Store の版でこの案内が出るかは未確認（[§8](#8-実機でしか切り分けられない点)）。

## 6. 検証

Issue の受け入れテストを、自動の試験と実機の確認に分ける。画像は登録済みの公開実画像（BBBC007・BBBC013・BBBC039・DS6a）を使う。破損した試料は、Issue と同じ作り方（公開 BBBC013 の先頭 32 バイト）で試験の中で作る。ファイル名だけに依存する経路の単体試験は、今の試験と同じ最小のバイト列（合成）を使い、試験名に明記する。

| Issue の受け入れテスト | 自動の試験 | 実機・人による確認 |
|---|---|---|
| 説明書なしで画像を追加し、AI へ進める | E2E：空の作業 → フォルダーの追加 → 一覧 → 追加 → 画像（⑥） | 初見の研究者による評価（迷った箇所と支援の回数）。未実施として追跡する |
| 4 枚＋1 枚で 5 枚が残る。2 群 6 枚を割り付けられる | 単体：選択の積み上げと取り消し（①・⑥）。E2E：DS6a の 6 枚 → 案 → 2 群各 1 視野・3 チャンネル（⑦） | フォルダーピッカーの選択・取り消し（[§8](#8-実機でしか切り分けられない点)） |
| 正常 4 枚＋破損 1 枚で 2 視野へ進める。再起動後も識別でき、1 枚だけ再試行できる | 単体：対照試験 B・C の回帰（①）。契約：`rejected` の票で比較が止まらず、内訳に残る（②）。E2E：再読込後に名前と理由が出て、差し替えで同じ票が解ける（②） | インストールした版で、再起動をはさんで確かめる |
| 注釈・説明が混ざっても内訳が合う。重複・上限・切断がほかの選択を消さない | 単体：内訳の合計（I-3）、対照試験 A の回帰（⑥）。API：受け取りの役割と理由コード（⑤） | — |
| 「チャンネルを教えて、まだ測らない」→「核染色は DRAQ」→「全視野で核を数えて」 | API：偽の提供元で `answer`・`settings`・`run`、形の誤り、チャンネルの不一致（⑧。今の拒否の試験 `tests/test_proposals.py` を広げる）。単体：`answer` でジョブ 0・設定の変更 0（⑧）。E2E：作業 A → B → A で発言が正しく戻り、再表示で外部の呼び出し 0（③） | 本番のモデルでの確認（有料。オーナーの許可が要る） |
| 解析の開始直後・画面の切り替え・通信断・更新通知で、状態と次の操作が分かる | 単体：ステップから視野の状態（⑨）、応答なし・401・403 の区別（⑩）、更新の失敗の段階（⑪） | 隔離した更新の試験（「後で」、解析中、二重クリック、起動の拒否、タイムアウト、0 以外の終了） |

各 PR で `cytellect-verify`（関係する検証だけ）を実行し、画面を変える PR は `cytellect-screen-check` で実際の画面を撮る。CI の成功は、研究者にとって使いやすいことの証明ではない。

## 7. オーナーの判断が必要な点

| | 判断 | 推奨 | 理由 |
|---|---|---|---|
| D1 | 技術的に登録できなかった画像を、理由の入力なしで記録し、比較を止めないか | 採用。API が理由コードを記録した票（`rejected`）と、送信が終わらなかった票（`pending`）の両方で止めず、群ごとの件数と理由を結果に残す。控えめな案：`rejected` だけ止めない | 黙って除くのではなく、記録して見せる。研究者が書いた理由より、読み取り処理が出した理由のほうが記録として正確 |
| D2 | 初手を画像の追加にし、1 画面・2 画面の選択を画像の後にするか（U01 の 2026-10-25 の改訂と E-01 の 2026-10-28 の決定を改める）。受け取りを API に置く（B）か | どちらも採用 | 画像が見えてからのほうが、実験デザインを決めやすい。B は再読み込みと Web アプリ化で作り直しがない |
| D3 | 同一内容のコピーを、既定で 1 つにまとめるか（I12 の 2026-10-06 の決定を改める） | 採用。別の撮影として追加する操作は残す | 視野数が観測数として読まれるため、既定は水増ししない側にする |
| D4 | 空の作業に見本の縮小画像を置くか | 案の画像を見てから決める | 画面の要素が増える。#258 は説明で画面が埋まり却下された |
| D5 | 解析案に `intent` を加え、応答の自動の適用と試行（L02）を改めるか。段階 2 の前に単独で入れるか | 採用。単独で入れる | 質問に答えないことは初回の作業を止める。段階 2 を待つと長い |
| D6 | 指示の原文と回答を、この PC のデータベースに保存するか（保存期限は作業データと同じ） | 採用 | 保存しないと、開き直したときに会話を戻せない |
| D7 | 更新案内の「後で」の長さ | その起動の間 | 次に開いたときに 1 回だけ思い出せる |
| D8 | 段 1 の ①・②・③ を先に進めてよいか。担当の分け方 | ① と ③ から始める（どちらも仕様の改訂が小さい。③ は D6 だけ） | 最優先の症状のうち、判断の少ないものから止める |

## 8. 実機でしか切り分けられない点

| 症状 | 分かっていること | 次の手順 |
|---|---|---|
| フォルダーで受け取れない | フォルダーの入力は `webkitdirectory` を付けた `input`（`CW:501`・`587`）。空のリストでは何も表示しない（`CW:355` の `files.length`）。観測は Edge の拡張機能経由で、手動の操作では未確認 | Issue の ①〜③ の順（`change` の発火 → `files.length` → 保留の件数）で記録する。⑥ では、0 件・全件対象外・取り消しを一覧に出し分ける（どの原因でも「何も起きない」をなくす） |
| サービスの停止（`Failed to fetch`、8765 に待受なし） | ブラウザ側は応答のない失敗として受け取る。停止の契機は未特定 | ローカルの API のログと Windows のイベントを、停止の時刻で突き合わせる。⑩ はどの契機でも同じ案内と再接続にする |
