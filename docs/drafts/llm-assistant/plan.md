# LLM による解析支援の設計の見直し（案）

状態：2026-11-16 にオーナーが「LLM に研究データを示すのは自然なことで、保守的な設計そのものが品質を下げている。設計全体を見直す」と指示し、同日、この案のとおり実装するよう指示した。§7 の判断 1〜4 と 6 は推奨のとおり採用したものとして扱う。判断 5（予算の値）はオーナーが別に決め、それまでは本番の今の値を変えない。実装は段階 0 と段階 1 から進め、関係する要件と文書は実装と同じ PR で改める。本番へのデプロイ、Windows 版の配布、有料の評価は、これまでどおりそれぞれ許可を得て行う。

## 1. 結論

今の設計は、LLM を「研究データをほとんど見せずに、決められた選択肢から 1 つを選ばせる部品」として扱っている。画像も、チャネル名も、測定値も見せていない。その結果、LLM は研究者の状況を理解できず、一般論の提案と、短く制限された考察しか返せない。

見直しの方針は次の 3 つ。

1. **見せる**：研究者が同意したら、画像、チャネル名やファイル名などのメタデータ、測定値の要約、研究者の付けた名前を、LLM にそのまま示す。
2. **対話させ、道具を使わせる**：1 回の呼び出しで JSON を埋めるのをやめる。研究者と対話し、画像を見て、解析パッケージの関数（試行の検出、測定、統計）を道具として呼ぶ研究アシスタントにする。
3. **守るのは「科学の正しさ」と「同意」に絞る**：送る量を減らして守ることはやめる。代わりに、次の 3 つを守る。
   - 結果として示す数値は、解析パッケージが計算したものだけにする。
   - 研究者が何を送るかを知って同意している。
   - 送った先で、保存も学習もされない。

## 2. 今の制約の仕分け

今の制約を 1 つずつ、品質を下げているか、何を守っているかで分けた。

### 2.1 外す・緩める（品質を下げている）

| 制約 | 今の扱い | 品質への影響 | 見直し |
|---|---|---|---|
| 画像を送らない | Worker は 512 px 以下・6 枚までの縮小画像を受け取れるが、ローカルの API が送らない。提案のプロンプトは「メタデータだけでは閾値の最適化も、マスクの確認もできない」と自ら断っている | LLM は染色の局在、飽和、ピントの外れ、検出の失敗を見られない。検出条件の提案が当て推量になる | 視野の画像、検出結果の輪郭を重ねた画像、拡大した領域を送る。どの画像を見るかは LLM が道具で選ぶ |
| チャネル名・ファイル名・メタデータを伏せる | チャネルは `c1` のような記号に置き換え、ラベル、ファイル名、メタデータの値は送らない | ファイル名やフォルダ名に書かれた条件・実験回・染色を読めない。研究者が名前を付けた意味が失われる | OME のメタデータ、チャネル名、ファイル名、フォルダの構成をそのまま送る。条件と実験回の割り当ての提案に使う |
| 測定値を見せない | 解析提案には測定値を一切送らない。考察には群と実験回の集計値だけを送る | 外れ値、視野ごとのばらつき、検出の失敗による値の偏りに気づけない | 視野ごと・核ごとの分布の要約、欠測、警告を送る。必要なら道具で個々の値を見る |
| 研究者の付けた名前を伏せる | 実験回を `run 1`、`run 2` に置き換え、結果の見出しも送らない | 研究者の言葉で書けず、結論ともつながらない | 実験回の名前、群の名前、見出しをそのまま送る |
| 指標の意味を伝えない | 指標のキー（`positive_fraction`）と英語の単位だけを送る | 陽性率の分母（判定できた核）などを取り違えるおそれがある | 指標の定義（日本語の名前、分母、プロトコルの版）を、画面・図と共通の台帳から送る |
| 単位を 20 文字までに制限する | 陽性数・陽性率の比較では考察を作れない | 研究上とくに重要な結果で考察が出ない | 上限を外し、単位を理由に考察を拒否しない |
| 考察を短く制限する | 3 つの見出しに各 1〜3 文、1 文 約 60 字 | 解釈の筋道（なぜそう言えるか）を書けない | 長さは研究者が選ぶ。根拠と推論の筋道を書かせる |
| 遺伝子・経路・薬剤の名前と文献を禁じる | 入力にない名前と、文献・DOI を出力させない | 生物学的な解釈と、次の実験の提案が一般論になる | 名前は許す。文献は Web 検索で実在を確かめた場合に限り、出典つきで示す（§4.3） |
| 決められた選択肢からしか選ばせない | 解析の型、指標、検定、図を列挙型の中から選ぶ。自由な説明の欄がない | 研究者の問いに合う解析がないときに、理由も代わりの方法も言えない | 実行する設定は今の契約のまま検証する。それとは別に、説明・質問・助言を自由な文章で返す欄を設ける |
| 1 回で終わる | 1 回の呼び出しと最大 1 回の修正。会話を続けられない | 研究者が聞き返せない。LLM も不明な点を確かめられない | 対話にする（§3） |
| 既定で無効、送るたびに確認 | 利用者が有効にし、送るたびに `transmission_confirmed` を求める | 使い始めるまでの手間が多く、使われない | 最初に 1 回、送る範囲を示して同意を得る。設定画面でいつでも変えられる |
| 予算が小さい | 月 $5、端末ごとに月 50 回 | 画像と対話を使うと、すぐ上限に届く | Anthropic API のクレジット（月 $100 相当）に合わせて上限を見直す |
| 応答のモデル名を 1 つに固定する | 配布済みの版は `gpt-6.1-sol` 以外を拒否する | モデルを替えるたびに Windows 版の配布が要る | 許可したモデルの一覧で照合する（[#227](https://github.com/genellect/cytellect/issues/227)） |

### 2.2 守り続ける（保守性ではなく、製品が保証すること）

| 制約 | 守る理由 |
|---|---|
| 結果として示す数値・マスク・p 値は、解析パッケージだけが計算する | AGENTS.md の「常に守ること」と、論文に使える結果を出すという製品の約束。LLM は道具を呼んで計算させてよいが、自分で計算した値を結果として示さない。LLM の文章（考察・提案の説明）の中の数値は検査しない（2026-11-17、[§8](#8-2026-11-17-の見直し考察の検証をやめ文脈を渡す)） |
| 原画像の画素値を変えない | 測定の前提 |
| 有意差を得るための調整をしない | 統計の正しさ。解析パッケージの統計の手順で守る。LLM の文章の言い回しを検査して止めることはしない（2026-11-17、[§8](#8-2026-11-17-の見直し考察の検証をやめ文脈を渡す)） |
| 実行する設定は検証してから、研究者が採用する | LLM の提案で、解析を勝手に実行・上書きしない |
| 研究者が送る範囲を知って同意している。プライバシーポリシーに書いた範囲を超えて送らない | 利用者との約束。範囲を広げるときは、先にポリシーを改め、利用者に示す |
| 送り先に保存・学習させない。Cytellect のクラウドに研究データを保存しない | 提供元の API の条件で担保する。保持期間はポリシーに正確に書く |
| API の鍵は Worker だけが持つ | 鍵の漏えいを防ぐ |
| 開発（Git、CI、ログ、開発用 AI）に非公開データを入れない | 製品の機能とは別の、開発の規則（[チーム開発ルール §6](../../team-development.md#6-研究データの扱い)）。この見直しの対象外 |

## 3. 新しい構成：研究アシスタント

```text
Browser（研究者との対話）
  ↕
local API：対話の進行と道具の実行（研究データは PC に残る）
  ├─ 道具：視野・チャネル・メタデータの一覧、画像と輪郭の取得、
  │        測定値の要約、代表視野での試行、設定の提案、統計、図
  ↕ 1 回の呼び出しごと
Cytellect Worker：鍵、予算の確保と精算、利用者の認証（本文は保存しない）
  ↕
Anthropic Messages API（Claude、道具の使用、画像入力）
```

- **対話の進行は PC 側に置く。** 道具は PC 上の研究データを読むため、対話の進行と道具の実行は local API が行う。Worker は今と同じく、1 回の呼び出しごとの中継と予算の管理だけを行う。将来のクラウド版でも同じ構成にする。
- **道具が数値を作る。** LLM は「代表視野で核を検出する」「この 2 群を比べる」などを道具として呼ぶ。数値はすべて解析パッケージが計算し、記録に残る。
- **設定の変更は研究者が採用する。** LLM が提案した設定は、今と同じく検証してから画面に示し、研究者が採用して初めて全視野に適用する。
- **画像は LLM が選んで見る。** すべての画像を最初に送るのではなく、LLM が道具で視野・チャネル・拡大する領域を選ぶ。費用と速度のためでもある。
- **考察も同じ対話の中で作る。** 保存した結果について、研究者が聞きたいことを聞ける。考察の文は検査で止めず、書かれたまま示す（2026-11-17 に改めた、§8）。

## 4. 変える内容

### 4.1 入力

- 画像：視野の画像（チャネルごと、LUT は表示用と明示する）、検出の輪郭を重ねた画像、拡大した領域。解像度は道具の引数で選ぶ。
- メタデータ：OME のメタデータ、チャネル名、ファイル名、フォルダの構成、取得日。
- 測定値：視野ごと・核ごとの分布の要約、欠測、警告。道具で個々の値も見られる。
- 研究者の言葉：研究の目的、群・実験回の名前、結果の見出し、メモ。
- 指標の台帳：指標ごとの日本語の名前、単位、定義（分母、領域）、プロトコルの版。画面・図・LLM が同じ台帳を使う。

### 4.2 出力

- 実行する設定（解析の型、検出の条件、統計、図）は、今の厳密な契約（JSON Schema）に沿って返させ、ローカルで検証する。形式は Claude にプロンプトで示し、出力の形を強制する機能（構造化出力）は使わない（2026-11-17、オーナーの判断）。Worker が形を確かめ、崩れていれば 1 回だけ直させる。
- 説明・質問・助言・考察は自由な文章で返させ、そのまま示す。数値・言い回し・長さの検査はしない（2026-11-17 に改めた、§8）。計算した値は、解析パッケージの記録だけにある。
- LLM が生成した文章であることを、画面で常に示す。

### 4.3 文献

- Web 検索の道具で文献を探させる。示すのは、検索で実在を確かめ、DOI か URL を付けた文献だけにする。
- 文献は「関連する報告」として示し、Cytellect の結果を裏付けるものとしては示さない。
- 考察の文の中で既報に触れること（「既報と同様に〜」）は、科学的な考察の一部として止めない（§8）。出典つきの一覧として示すのは、上の検索で確かめた文献だけにする。

### 4.4 モデルと費用

- 解析提案と考察は、すべて Claude に統一する（2026-11-17、オーナーの判断）。配布済みの版（0.1.0-local.23 以前）は応答のモデル名を `gpt-6.1-sol` と照合するため、その版の要求だけは Sol のまま答え、新しい版への更新で Claude に移る。
- モデルは Claude Sonnet 5.5（`claude-sonnet-5-5`、入力 2・出力 10・キャッシュ読み出し 0.1・書き込み 2.5 ドル / 100 万トークン）とする（2026-11-17、オーナーの判断）。当初は Opus 5.5 を基本としたが、費用の見積もり（考察 1 回 約 0.04 ドル、解析提案 1 回 約 0.06 ドル。Opus はその約 2 倍）を見て決めた。質は公開事例の評価（[#227](https://github.com/genellect/cytellect/issues/227)）で確かめる。対話と道具の使用では、同じ前置き（システムプロンプト、道具の定義）が繰り返されるため、プロンプトキャッシュが効く。
- 費用は 1 回の対話で数十セントを見込む（画像 1 枚 約 1,400 トークン、対話全体で数万〜20 万トークン）。月 $100 で数百回の対話になる。実際の費用は評価で測る。
- 予算の仕組み（呼び出し前の確保、月ごと・利用者ごとの上限、超過時の停止）は残す。上限は月 50 ドル、1 人あたり月 5 ドルとする（2026-11-17、オーナーの判断）。本番への反映は Worker のデプロイ（オーナーの許可が必要）から。

### 4.5 同意と開示

- 最初に使うときに、送る範囲（画像、メタデータ、ファイル名、測定値の要約、入力した文章）と送り先、送り先での扱いを示し、1 回同意を得る。
- 設定画面で、画像を送るかどうかなどを個別に切り替えられるようにする。
- プライバシーポリシー、SECURITY、[データ保護と運用](../../security.md)を、送る範囲に合わせて先に改める。

## 6. 品質の確かめ方

- 公開画像の場面ごとに、提案・考察の評価の事例を作る。評価の観点は次のとおり。
  - 研究者の状況（染色、条件、実験回）を正しく読めているか。
  - 提案した検出条件で、代表視野の検出が改善するか。
  - 考察が生物学的に妥当か。
  - 数値と統計の規則に反していないか。
- 今の設計（Sol、限られた入力）と新しい設計を、同じ事例で比べる。評価データを見てプロンプトを調整しない。
- 研究室の実画像での確認は、オーナーが指定した隔離ローカル環境で行い、公開側には判定と匿名化済みの集計だけを戻す（[チーム開発ルール §6](../../team-development.md#6-研究データの扱い)）。

## 7. オーナーの判断が必要な点

1. **方針**：§1 の 3 つの方針と、§2 の仕分け（外すもの・守るもの）を採用するか。
2. **送る範囲**：画像、ファイル名とフォルダの構成、測定値の要約、研究者の付けた名前を、同意を得たうえで送ってよいか。送らない項目を残すか。
3. **同意の取り方**：最初に 1 回の同意と、設定画面での個別の切り替えにするか。
4. **文献**：Web 検索で確かめた文献を示してよいか。
5. **予算**：月の上限（今は月 $5）と、利用者ごとの上限をいくらにするか。→ 2026-11-17 に決定：月 50 ドル、1 人あたり月 5 ドル。モデルは Claude Sonnet 5.5（§4.4）。
6. **順序**：段階 1 を Claude への移行（#227）と一緒に進めるか。

## 8. 2026-11-17 の見直し：考察の検証をやめ、文脈を渡す

状態：2026-11-17 にオーナーが承認した（下の 1〜5 すべて）。同じ日に genellect/cytellect#231 で実装した（§8.6）。

### 8.1 オーナーの判断

- 「はじくというルール自体が、LLM の出力を止めるバグを誘発する。数値は計算結果以外にも現れるのが科学であり、それを制限するのは逆に恣意的な結果やバグを招く」
- 「注記そのものが AI 生成っぽい適当な表示になり、UI の完成度を下げる」
- 「コンテクスト（計算結果や生成した結論など）は出来る限り LLM にわたすべきで、余計な検証が全体的に不要。生物学的な妥当性を守るとは、制限をかけることではない」

### 8.2 現状（2026-11-17 時点）

| 段階 | 仕組み |
|---|---|
| 入力 | 保存した 2 群比較の数値（群の平均、差・比と区間、実験回ごとの値、n、検定、p 値、警告）、指標の名前と定義、群・実験回・チャネルの名前、研究者が入力した目的 |
| 渡していないもの | 画面の結論の 1 行（`heading` の欄はあるが API が常に空にする）、観測数・視野数・試料数（`counts`）、集計と検定の方法（`method_settings`）、AI への相談で書いた研究の目的、図、同じ実験のほかの指標 |
| 出力の制限 | 3 つの見出しの文のリスト、1 項目 400 字、4・3・4 項目まで |
| 検証 | 結果にない数値、記述統計での「有意」など、区間が 0 を含むときの「変化がない」など、文献・リンク。1 か所でも当たれば考察全体を表示しない（`discussion_validation.py`） |
| プロンプト | 上の規則を「回答の後で検査する」と明示し、文献を禁じる（`services/proposal-worker/src/discussion.ts`） |

### 8.3 課題

1. **正しい文を止める**：科学的に正しい次の 6 文を今の検証に通すと、すべて弾かれた（2026-11-17 に確認）。規則が単語と数字の表面を見るため、否定・慎重な言い方・次の実験の条件・既報への言及を区別できない。慎重で正確な文ほど弾かれる。
   - 検定は行っていないため、有意差の有無はこの結果からは言えない。（有意）
   - 区間が 0 を含むため、変化がないとは言えない。（変化がない）
   - 既報（Lens et al.）と同様に、PLK1 の欠失は分裂期の停止を起こす可能性がある。（文献）
   - 24 時間後と 48 時間後の時間経過で確かめる必要がある。（結果にない数値）
   - 確認された事実ではなく、仮説である。（有意）
   - 核数が約 5 分の 1 になったことは、増殖の停止と整合する。（結果にない数値）
2. **直すほど規則が増える**：2 日で 3 回、誤判定の例外を足した（単位の文字数、名前の中の数値、遺伝子名と序数）。それでも上の 6 文は通らない。
