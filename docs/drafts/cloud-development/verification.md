# 本番構成での動作確認と研究者 UX 評価：実施計画（案）

作成：2026-10-27。状態：オーナーの承認待ち。

[クラウド開発環境の実装計画](plan.md)の環境が整った後に、研究室の PC と同じ構成を起動して、2 種類の確認を行うための計画です。

| 種類 | 目的 | 実施者 | 証拠になるもの |
|---|---|---|---|
| 動作確認 | 全部品（Fiji、GPU 推論、解析提案、測定、統計、図）が、本番構成で公開画像を最後まで処理できること | エージェント（自動の試験と、画面の通しの操作） | 試験の結果、記録（件数、所要時間、ハッシュ） |
| 研究者 UX 評価 | 画像解析に詳しくない研究者が、目的を定め、原画像を確かめ、実験単位を保った図を作れること | 研究者と観察者 | 課題ごとの結果、停滞、支援、本人の説明 |

自動の試験の成功や見た目の改善は、人による使いやすさの証拠に数えません（[Wet研究者による操作評価課題](../../usability-tasks.ja.md)）。2 つの結果は分けて記録し、報告します。

## 1. 開始の条件

次がすべて満たされてから始めます。

| 条件 | 確かめ方 |
|---|---|
| 実装計画の R1〜R6 が満たされている | [実装計画](plan.md)の WP1〜WP6 が `main` に入っている |
| 外部サービスがすべて使える | `python3 scripts/dev.py doctor --live --require-cloud` がすべて `[ok]` |
| 公開画像だけを受け付ける | 共有の起動で `CYTELLECT_UPLOAD_ALLOWLIST` が有効。一覧にない画像の登録が 403 になることを、最初に一度確かめる |
| 実施する版が決まっている | `main` のコミットの SHA と、Web のビルドの SHA を記録する。評価の途中で版を変えない |

## 2. 起動と後片付け

1. 新しいクラウドセッションで `doctor --live --require-cloud` を実行し、結果を記録する。
2. `python3 scripts/dev.py serve --share` で起動する。作業データは回ごとに新しい場所にする。
3. 参加者ごとに招待コードを発行する。有効期限は、評価の枠と同じ長さにする。
4. 終了したら共有を止め、作業データを削除する。記録には集計値だけを残す。

## 3. 動作確認

段階ごとに進めます。前の段階が失敗したら止め、原因を記録して直してから再開します。失敗した視野や場面を、黙って除外しません。

| 段階 | 内容 | 使う画像 | 合格の条件 | 費用 |
|---|---|---|---|---|
| D0 準備 | `doctor --live --require-cloud` | なし | すべて `[ok]` | GPU の起動 1 回 |
| D1 核の検出 | `pytest -m fiji` と、画面の通しの試験（`pnpm test:e2e`、実際の Fiji） | BBBC007、BBBC013 | 失敗 0 件。BBBC007 の記録が参照と一致 | なし |
| D2 GPU 推論 | `scripts/cellpose_remote_check.py`。CPU の結果と比べる | BBBC013 A01 | 200 が返り、検出数と版のハッシュが記録と一致 | 数分の GPU |
| D3 解析提案 | 固定の公開場面の評価（`proposal-worker` の `eval:public`、12 場面） | 公開場面の文脈 | 全場面が検証を通り、期待した設定になる | 12 回分の呼び出し（上限内） |
| D4 画面の通し | エージェントが画面を操作し、登録 → 検出 → 修正 → 測定 → 統計 → 図の書き出しを、核、核小体（GPU）、解析提案の 3 経路で行う | BBBC007、BBBC013、JUMP | ページのエラー 0 件。図と Methods が出力され、図の点から元の画像に戻れる | 少数の GPU と提案 |
| D5 研究者の課題の予行 | 研究者 UX 評価の課題 1〜5 を、エージェントが課題文どおりに通す | 課題の画像 | 全課題が最後まで進む。詰まった箇所を記録する | 少数の GPU と提案 |

D4 と D5 の画面は、各段階の主要な画面だけをスクリーンショットに残します。研究データ、認証情報、招待コードは写しません。

## 4. 研究者 UX 評価

[Wet研究者による操作評価課題](../../usability-tasks.ja.md)の課題 1〜5 と記録の項目を、そのまま使います。クラウドでの実施に合わせて、次を決めます。

| 項目 | 内容 |
|---|---|
| 参加者 | 異なる研究室の 3 名以上。Fiji の日常使用、時々使用、未経験を記録する |
| 予行 | 本番の前に、オーナーが参加者役で 1 回通し、課題文と所要時間を確かめる |
| 実施の形 | 参加者は自分のブラウザで共有の URL を開く（Access で本人確認）。観察者はビデオ通話で画面共有を見る。録画は参加者の同意があるときだけ |
| 画面 | デスクトップの画面幅で行う。スマートフォンは、結果と元画像を探す追加観察だけにする |
| 画像 | 課題ごとに用意した公開画像だけ。参加者本人の画像は使わない（一覧にない画像は API が拒否する） |
| 記録 | 課題ごとに、自力完了、説明支援で完了、操作支援で完了、未完了、安全上重要な誤解に分ける。所要時間、停滞、支援、本人の説明を残す。研究テーマ、所属、認証情報は残さない |
| 開始状態 | 課題ごとに新しいワークスペースから始め、前の課題の失敗が次に影響しないようにする |

## 5. 実装すること

| 番号 | 内容 | 依存 |
|---|---|---|
| V1 | `dev.py serve --share`（実装計画の WP4）。SIGTERM と SIGHUP でも子プロセスを止める。共有のときは受け付ける画像の一覧を必ず有効にする | WP3、オーナーの作業 |
| V2 | 回ごとの作業データの作成と削除、参加者ごとの招待コードの発行を、`serve --share` の操作に含める | V1 |
| V3 | 課題の画像の一式。課題 1〜5 が使う公開画像（BBBC013、BBBC007、JUMP）を準備し、受け付ける一覧に登録する。出典、染色、利用条件を同梱する | なし |
| V4 | `dev.py verify`：D0〜D3 を順に実行し、集計だけの記録（件数、所要時間、ハッシュ、費用）を残す。D3 は費用の上限を指定したときだけ実行する | V1 |
| V5 | 操作評価の課題の文書を、クラウドでの実施に合わせて更新する。今は Windows 版 0.1.0-local.11 を対象にしている | V1〜V3 |
| V6 | 結果の記録先。動作確認の結果は roadmap に、研究者 UX 評価の集計は評価の文書に残す | D0〜D5 |

V3 と V5 は、オーナーの作業を待たずに始められます。

## 6. 費用

| サービス | 使う量 | 上限 |
|---|---|---|
| GPU 推論（Modal） | D0、D2、D4、D5 と、評価の各回で起動する。起動にかかる時間は GPU の空き次第で、使用後 20 秒で止まる | Modal の無料枠と、使用上限 30 ドル |
| 解析提案（OpenAI） | D3 の 12 回と、D4、D5、評価で使う回数 | Worker の月 5 ドルの予算と、端末ごとの月の回数 |

各段階の実際の費用を記録し、評価の回数を決める材料にします。上限に近づいたら止めて、オーナーに相談します。

## 7. 報告

次を分けて報告します。

- 実装（V1〜V6）
- CI
- 動作確認（D0〜D5）
- 研究者 UX 評価（課題 1〜5）

失敗、未実施、支援を受けた完了を、合格として扱いません。結果は roadmap に記録し、見つかった不具合と改善点は、それぞれ別の PR か Issue にします。

## 8. オーナーに決めていただくこと

- 参加者の募集と日程、同意の取り方（録画の有無を含む）
- 評価に使う費用の上限
- 実施する版（`main` のどのコミットで行うか）
- 観察者（オーナーか、別の人か）

## 9. 危険と対策

| 危険 | 対策 |
|---|---|
| 参加者が自分の研究画像を登録しようとする | API が一覧にない画像を拒否する。課題の説明でも、使う画像を指定する |
| 評価の途中で GPU や解析提案が止まる | 開始前に D0 を実行する。止まった場合は課題を中断し、未完了として記録する。合格には数えない |
| 共有の URL が評価の外に広まる | Access で本人確認をし、招待コードと共有の期限で守る。終了後に共有と作業データを消す |
| 自動の確認の成功を、使いやすさの証拠と取り違える | 動作確認と研究者 UX 評価を、別の表と別の報告にする |
