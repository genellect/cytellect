# 群間比較の UX 改善：目標定義書（案）

作成：2026-10-25。改訂：2026-10-25（オーナーの回答を反映）、2026-10-25（Codex の独立レビュー（対象コミット `21f6d0f`）を反映）。**2026-10-25 にオーナーが承認し、実装中です。** この文書は、上位の目標・範囲・完了条件を定めます。画面の設計や API の変更（実装案）は扱いません。要件の詳細は[要件定義書](requirements.md)、並行実装の進め方は[開発体制](development.md)にあります。

## 1. 決定事項

オーナーが 2026-10-25 に回答した内容です。

| ID | 質問 | 回答 | この文書での扱い |
|---|---|---|---|
| Q1 | 「1 画面制／2 画面制」は、解析の形と画面の分割の両方を指すか | はい | 1 画面 = 1 群の記述、2 画面 = 2 群の比較。選んだ形が、画面の分割と比較の意図の両方を決める。比較の設計の確認（S10）は省かない |
| Q3 | 「実験日を固定」は、実験日を n の単位にし、同じ日の群どうしを対にして比べる意味か | はい | 独立した実験の 1 回（実験回）を n とし、既定では実験日で名付ける。同じ実験回の 2 群を対にする。日付・プレート名・反復番号だけから独立性を推定しない |
| Q4 | 「DAPI 5 視野、GFP 5 視野…」は別々の視野か、同じ視野の別チャンネルか | 同じ視野・同じカバーガラスを意図する | 1 つの視野を、複数の染色（DAPI、GFP、NCL、CellMask など）のチャンネルで撮影した画像として扱う。チャンネルを別々の反復や別々の視野に数えない。対照群と処理群が同じ細胞を共有するとは扱わない |
| Q5 | 画像の追加の前に設定を出さないという要件 U01 を見直すか | 合意 | 最初に 1 画面／2 画面を選び、画面（群）ごとに画像を追加する |
| Q6 | 入力の上限（視野数、チャンネル数）を引き上げるか | 合意 | 1 視野 4 チャンネル以上を受け付ける。具体的な値はメモリと時間を測って決め、I07 と I09 を一緒に更新する |
| Q7 | デモで最初に見せる変化はどれか | 核の縮小。ただし、核数・核小体の変化もデモで一通り再現できるようにする | 既定の場面は核の縮小。核数の変化と核小体の変化の場面にも切り替えられる |

2026-10-25、オーナーは独立レビューの反映後、[§8](#8-判断が必要な事項) の Q2、Q8–Q15 を提案どおりとし、3 つの下書き（この文書、[要件定義書](requirements.md)、[開発体制](development.md)）に基づく実装を指示しました。Q15 は提案が 2 案だったため、主担当が U2OS（DS6a）の核小体の形と 5-EU を示す案を選びました（ライセンスを確認済みで、現在のデモの仕組みを使えるため）。

## 2. 依頼の分解

| 依頼者の言葉 | 解釈 |
|---|---|
| デモと本番画面の UX/UI 改善 | 公開デモ（`/demo`）とローカル版のワークスペースを、同じ画面のまま改善する。デモ専用の画面は作らない（[公開デモ](../../showcase.md)は本番と同じ画面を使う） |
| 実際に行いたい解析（WT 群や薬剤処理群との同時比較、群間比較）ができない | 検定の計算は実装済み（[解析機能の概要](../../implementation-overview.ja.md)）。足りないのは、群と実験回を研究者の考える順序で入力し、群を並べて見比べ、比較を一続きで終える導線 |
| 必要な解析機能、統計・グラフに過不足がある | 生命科学で一般に見る指標（核数、陽性の割合、核小体の形、細胞質の面積など）が、研究者が選べる形でそろっていない。研究者の判断に使わない内部の値が、画面に多く出ている |
| 使い方が直感的に理解できない／統計解析画面が何を示しているのかわからない | 結果が「何を、どの n で比べ、どちらにどれだけ変わったか」という文で示されず、図・表・p 値が並ぶだけになっている |
| 最初に 1 画面制または 2 画面制を選ぶ | 1 画面：1 つの群の記述。2 画面：2 つの群を並べて比較する（Q1） |
| 群 1・群 2 で実験日を選択（固定）し、n 数を比較、統計検定する | 実験回ごとに、同じ回の 2 群を対にして比べる。n は実験回の数（Q3） |
| 1 つの群に複数の染色条件の視野を同時にアップロードできる。サーバー側は微調整 | 1 つの視野を複数の染色で撮影した画像を、群・実験回ごとにまとめて追加する。現在の視野とチャンネルの仕組みを使い、チャンネル数の上限を引き上げる（Q4、Q6） |
| 測りたい指標を迷わず選べ、妥当な群間比較のグラフを出力できる | 「何を知りたいか」から指標を選ぶと、指標ごとに妥当な集計・推定・検定・図が決まる |
| 公開データを探し、テスト・検証用データにする | 論文化され再配布できる公開画像で、対照と処理が同じ実験の中にあるものを、デモと回帰試験の共通データにする。定量の妥当性の検証には、別の評価データを用意する |
| デモで、薬剤処理群で核が明確に縮小していることが、初心者にも直感的にわかる | 出典の論文が報告している核の縮小を、2 群の画像の並置、測定から作った一文、図で示す。核数と核小体の変化も同じ形で確かめられる（Q7） |

## 4. 上位目標

**G0：画像解析に詳しくない Wet 研究者が、自分の実験（対照と処理、複数回の独立した実験）をその構造のまま入力し、知りたい変化に合う指標を迷わず選び、何を・どの n で比べ・どちらにどれだけ変わったかを理解したうえで、論文に使える群間比較の図と統計を得られる。**

これは[プロダクトの使命](../../development-principles.md#プロダクトの使命)の「何を対象に何を測っているかを理解し、明確な導線のもとで迷わず修正と判断を行い、統計と編集可能な論文の図まで同じ作業の中で完了できる」を、群間比較について具体化したものです。

## 5. 下位目標

| ID | 目標 | 達成した状態 |
|---|---|---|
| G1 | 実験の形を最初に選べる | 最初に「1 画面（1 群の記述）」か「2 画面（2 群の比較）」を選ぶ。画面ごとに群の名前を付け、実験回・試料ごとに、複数の染色で撮影した視野をまとめて追加できる。視野ごとの表に後から書き込む必要がない |
| G2 | 群を並べて見比べ、直せる | 実験回を 1 つ選ぶと、2 つの画面にその回の 2 群の視野が、同じチャンネル・同じ表示の変換・同じ物理的な倍率で並ぶ。検出した輪郭と測定値も並べて確認・修正でき、修正は依存する結果だけを更新する |
| G3 | 知りたい変化から指標を選べる | 「核が小さくなったか」「核が減ったか」「陽性が増えたか」「核小体が変わったか」などの問いから選ぶと、領域の定義・測る染色・対象・集約・推定・図が決まる。必要な染色がなければ、その理由が分かる |
| G4 | 結果が何を示すか分かる | 結果の先頭に、指標と手法に合った一文（何を比べ、n はいくつで、どちらにどれだけ変わったか）が出る。各実験回の変化の向きと、図の点が何を表すかが分かる |
| G5 | 論文に使える図と出力になる | 実験回を n とし、対応が分かる図を既定とする。論文でよく使う形も、全実験回の点を重ねる形で選べる。編集可能な SVG・PDF、元データ、Methods が一緒に出て、保存した結果と対応する |
| G6 | デモで初見の人に価値が伝わる | `/demo` を開くと、対照と処理の 2 画面が並び、変化が画像・一文・図で分かる。場面は核数（JUMP）と核小体（DS6a）の 2 つで、切り替えられる（核の縮小は条件を満たす公開データがないため公開しない。2026-10-25 のオーナーの判断）。どの変化も出典の論文が報告しており、図の点から元の視野・核へ戻れる |
| G7 | 公開データをデモと回帰試験に使う | デモに使う公開画像一式を、操作の再現・数値の整合・回帰試験のデータとしても登録する。出典・ライセンス・染色・実験の構造・ハッシュと、視野の選び方・除外の規則を、測定の前に記録する |

## 6. 範囲

**含む**：最初の 1 画面／2 画面の選択、群・実験回・試料・視野の入力、群の並置表示、指標の一覧と選び方、指標と手法に合った結果の文、図と出力、除外と品質の扱い、公開デモのデータと構成、それに必要な解析・API の変更（指標・推定値の追加、入力の上限の引き上げ）。

**含まない**：検出モデルの新規学習、3 次元・タイムラプス、斑点（foci）の検出、混合効果モデル、3 群以上の新しい導線、ホスト型での研究画像の受け付け、LP の変更。既存の 3 群以上の比較と、保存した結果の再生は使えるまま残します。

**変えない約束**：原画像の画素値を変えない。測定値と統計は、API と解析パッケージの共通実装だけが作る。n は独立した実験の繰り返しで、核数や視野数で n を増やさない。有意差を得るための視野・しきい値・手法の選び直しや、結果に応じた対象の除外をしない。

## 7. 完了条件

確認の方法を、自動検証（CI・ブラウザ試験）、参照計算（実装と独立に仕様から作った期待値）、目視（画面と出力の確認）、出典との照合、ローカルでの受入、研究者による評価に分けます。自動検証と目視は、研究者が使えることの証拠にはしません。研究者による評価も、自動検証や科学的な仕様との照合の代わりにはしません。要件ごとの担当・検証方法・合格条件は[要件定義書 §8](requirements.md#8-要件と検証の対応)にあります。

**前提**：C1・C6・C7 に使う公開データの識別子と実験の構造を、実装を始める前に確定します。確定していない場面の完了条件は未達とします。同じ視野の切り出しや別チャンネルを、独立した実験回として扱いません。

| ID | 完了条件 | 確認の方法 |
|---|---|---|
| C1 | 最初に 2 画面を選び、2 群 × 実験回 3 × 各 5 視野（各視野 4 チャンネル）を、視野ごとの表に戻らずに入力し、欠けた組み合わせの検出、1 画面からの移行、統計まで進める。既存の結果は失われない | 自動検証：確定した公開実画像でのブラウザ試験（画像を使う結合試験に合成画像は使わない。[開発の原則](../../development-principles.md#研究データと検証)） |
| C2 | 実験回を選ぶと、2 つの画面に同じ回の 2 群が、同じ表示の変換・同じ物理的な倍率で並び、変換と値が画面に示される。並べた状態で輪郭を直すと、依存する測定・統計・図だけが更新される | 自動検証、目視 |
| C3 | [要件定義書 §3](requirements.md#3-指標の一覧) の第一段階の指標を問いから選べ、定義・対象・欠測の扱いが確かめられ、必要な染色がない場合は選べない理由が出る | 自動検証 |
| C4 | 結果の文の数値が、(a) 保存した統計の値と一致し、(b) 実装と独立に仕様から作った参照値と一致する。手法ごとに、算出しない値を表示しない | 自動検証、参照計算 |
| C5 | 群間比較の既定の図が実験回を n として描かれ、点が何を表すかと集約の規則が凡例に書かれる。SVG・PDF・元データ CSV・Methods の内容が、保存した結果と一致する | 自動検証、目視 |
| C6 | `/demo` を開くと、追加の操作なしに、最初の場面（核数）の 2 画面の並置・結果の文・図が出る。核小体の場面にも切り替えられ、どの場面でもエラー表示がない。初回表示の時間と転送量が、[要件定義書](requirements.md) N-03 の基準を満たす | 自動検証（既存の受入テストの拡張） |
| C7 | 各場面について、比べる論文の図・指標・条件・集約の単位・比較できる範囲を測定の前に記録し、デモの変化の向きと大きさが記録と矛盾しない。矛盾した場合は原因を調べ、解消するか、オーナーが表示の目的を承認し直すまで、その場面を未達とする | 出典との照合（記録を残す） |
| C8 | デモと回帰試験のデータの一覧・選定の規則・除外の規則を、コミットとハッシュで固定し、探索に使ったデータも記録する。規則は、比較する測定値に依存しない | 自動検証（fixture の照合）、記録、レビュー |
| C9 | 初めて使う研究者が、デモの結果について「何を比べたか」「n は何か」「どちらに変わったか」を説明できる | 研究者による評価。対象者・人数・課題・支援の扱い・合格条件は、実施前にオーナーが承認する（Q14） |
| C10 | 研究者が自分の実験の形で、2 群の比較を図の書き出しまで、支援なしで終えられる | 同上 |
| C11 | 統合後の固定したコミットで、ローカル版（Windows）でも C1・C2・C5 の流れが動く | ローカルでの受入 |

C1–C8 と C11 はエージェントの作業で確かめます。C9・C10 は人の評価が必要で、満たすまで [roadmap](../../roadmap.md) の未完了の受入条件に残します。CI の成功、ローカルでの動作、出典との照合、研究者の評価、公開は、それぞれ別の事実として報告します。

## 9. 進め方

1. **定義の承認**：2026-10-25 に完了（Q1–Q15 を決定）。
2. **独立レビュー**：Codex のレビューを [§11](#11-独立レビューへの対応) のとおり反映した。オーナーの判断で、再レビューは行わない。
3. **公開データの選定と登録**：[要件定義書 §6](requirements.md#6-公開データ) の基準で候補を確かめ、場面ごとのデータと比較する論文の図を確定する。視野の選び方と除外の規則を測定の前に記録し、fixture にする。
4. **実装案**：画面の設計と、API・解析パッケージの変更点を決める。
5. **実装**：[開発体制](development.md)の分担で、Claude Code を主担当、Codex を補助として、目的ごとに PR を分ける。
6. **検証**：C1–C8・C11 を確かめ、C9・C10 を研究者の評価で確かめる。

## 10. 独立レビューの観点

再レビューでは、特に次の点を確かめてください。

- §11 の対応が指摘を解消しているか。新しい矛盾を生んでいないか。
- 依頼の解釈（§1、§2）と完了条件（§7）が、目標（§5）と要件を漏れなく覆い、確かめられる形になっているか。
- 要件が既存の科学的な約束（[要件](../../requirements.md)、[開発の原則](../../development-principles.md)）と矛盾しないか。
- 指標と表現型の生物学的な解釈、公開データの基準、[開発体制](development.md)が妥当か。
