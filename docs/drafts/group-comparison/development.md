# 群間比較の UX 改善：開発体制（案）

作成：2026-10-25。改訂：2026-10-25（Codex の独立レビュー（対象コミット `21f6d0f`）の代案を反映）。**2026-10-25 にオーナーが承認し、2026-10-26 に genellect/cytellect#110 で `main` に入れました。未完了の項目は[ロードマップ](../../roadmap.md)にあります。** [目標定義書](goals.md)と[要件定義書](requirements.md)を、Claude Code と Codex の 2 つのエージェントで並行して実装するときの、分担、コンフリクトの防ぎ方、相互レビューを定めます。[チーム開発ルール](../../team-development.md) §5 と [AGENTS.md](../../../AGENTS.md) を前提にし、これらと食い違う場合はそちらに従います。

## 1. 役割

| 役割 | 担当 | 責任 |
|---|---|---|
| オーナー | `@genellect` | 要件の確定、公開データの採用、マージ、公開、研究者評価の手配 |
| 主担当 | Claude Code | 全体の設計と統合、要件と API の契約、画面、除外と品質、図と出力、公開デモの生成、文書の整合、作業の分割と順序、PR の進行管理 |
| 補助 | Codex | 新しい指標と推定値の解析部品、公開データの調査と来歴の取りまとめ、ローカル版（Windows）での測定と受入、主担当の成果の独立した確認 |

主担当が作業の分割と順序を決めます。補助は、分割・順序・担当に異論があれば、着手前に PR のコメントかオーナーへの報告で示します。

## 2. 分担の考え方

分担は、モデル名から推測した得意・不得意ではなく、作業の性質と実行環境で決めます。「Claude は画面、Codex は数値に強い」といった比較評価は行っていません。

| 作業の性質 | 担当 | 理由 |
|---|---|---|
| 画面の大きなコンポーネントにまたがる変更、API の契約、統合、生成物 | 主担当 | 文脈が広く、分けるとコンフリクトと不整合が増える |
| 入力・出力と受入の試験が明確な解析部品（新しい指標、推定値） | 補助 | 契約が決まれば独立に作れ、参照値で正しさを確かめられる |
| 独立性が価値になる作業（参照計算、レビュー） | 実装していない側 | 同じ担当が実装と照合を行うと、同じ誤りを見逃す |
| 実行環境に依存する作業（Windows、Fiji、Cellpose、ブラウザでの受入、ネットワークでの取得） | その環境を持つ側 | 下の表で確かめた環境に合わせる |

## 4. コンフリクトを防ぐ規則

### 4.1 ブランチと PR

- 1 つの PR に、実装の責任者を 1 人だけ置く。2 人が実装する WP（WP7 など）は PR を分ける。
- 1 つの PR を 1 つのブランチ・1 つの worktree で行う。主担当は `claude/…`、補助は `codex/…` を使う。
- 互いのブランチには push しない（チーム開発ルール §3）。直してほしい点は PR のコメントで伝え、担当が直す。
- PR の説明に、基準のコミット（main の SHA）と、依存する PR とその SHA を書く。

### 4.2 ファイル単位の所有

所有はファイル単位で決めます。節が違っても、同じファイルを 2 つの PR で同時に変えません。

| ファイル | 所有 |
|---|---|
| `apps/web/src/components/workspace/**`、`apps/web/src/lib/**`（生成された型を含む）、CSS | 主担当 |
| `packages/contracts/**`、`packages/analysis/src/cytellect_analysis/*contracts*.py`、OpenAPI、既定レシピ | 主担当 |
| `services/api/**`、`services/worker/**`（API の接続と実行処理） | 主担当 |
| WP0 の契約：`experiment_design.py`、`group_comparison_contracts.py`、`tests/test_experiment_design.py` | 主担当 |
| WP3・WP4 の実装：`field_summary.py`、`nucleolar_shape.py`、`comparison_estimates.py` と `tests/test_group_comparison_metrics.py` | 主担当（2026-10-25 にオーナーが補助から移管。補助は仕様からの照合とレビュー） |
| WP10 の参照値：`tests/test_group_comparison_reference.py` | 主担当 |
| `packages/analysis/src/cytellect_analysis/` の既存の統計・図・集計のモジュール（`common_statistics*.py`、`common_unit_inference.py`、`region_comparison*.py`、`compartment_*.py`、`figures.py` など）と、新しい部品をそれらへ接続する変更 | 主担当 |
| `tests/conftest.py` など試験の共通設定 | 主担当 |
| `uv.lock`、`pnpm-lock.yaml`、`pyproject.toml` | 主担当（依存の変更だけの PR で） |
| `apps/web/public/showcase/**`、`services/showcase/**` | 主担当 |
| `fixtures/public/**`、公開データの登録・許可一覧、取得用のスクリプト | 補助（WP8） |
| `docs/methods.md`、`docs/common-statistics.md` | 主担当。WP3・WP4 の PR の間だけ、明示して補助に移す（4.3） |
| `docs/requirements.md`、`docs/roadmap.md`、この下書き | 主担当 |

各 PR の着手前に、変更する予定のファイルと、共有の接続箇所（登録口、API の経路、試験の共通設定など）を PR の説明に書き、相手側が重なりを確かめます。

### 4.3 WP0 の成果と WP3・WP4 の着手点

WP0 は、契約と雛形を次のように用意した。定義の正本は[計算仕様](../../methods.md)の「Group comparison contracts」の節。

| 補助が実装する関数 | 契約 | 仕様の節 |
|---|---|---|
| `field_summary.field_summary_values(fields, selection)` | `FieldSummarySelection`、入出力の型は同じファイルの `FieldInput`・`FieldSummaryRow` | Field-summary selection 1.0.0 |
| `nucleolar_shape.nucleolar_eccentricity(nuclei, nucleoli)` | 出力の型 `NucleolarShape`、選択は `CompartmentSummarySelectionV11` | Compartment-summary selection 1.1.0 |
| `comparison_estimates.comparison_estimates(control, treatment, …)` | `ComparisonEstimates`、尺度は `metric_scale` | Comparison estimates 1.0.0 |

- 補助は、関数の名前・引数・戻り値の型を変えない。変える必要がある場合は、着手前に PR のコメントで主担当に依頼する（契約は主担当の所有）。
- 雛形の関数は `NotImplementedError` を送出する。新しい観測の元と推定値は、補助の実装がマージされた後に、主担当が API とワーカーへ接続する。それまで、API は受け付けず、画面にも出さない（N-07）。

### 4.4 所有の移管

- 所有を移すときは、移す範囲、基準のコミット、その時点の検証の結果を PR のコメントに書く。
- 移している間、元の所有者はそのファイルを変えない。PR がマージされるか閉じられたら、所有は元に戻る。WP3・WP4 の PR の間、`docs/methods.md` の該当の節の文案の調整は補助が行う。
- 生成物は、生成元と同じ PR で、所有者 1 人が作り直して整合させる。コンフリクトした生成物を手で統合しない。

### 4.5 契約・版・マージの順序

- **契約を先に決める。** WP0 で契約と仕様を固め、補助のレビューを経てから並行作業を始める。
- **契約の追加は後方互換にする。** `main` へのマージは本番の自動デプロイを起動するため、先にマージする契約は既存の動作を変えず、実装が終わっていない機能を画面に出さない。
- **版と互換性の対応表を作る。** 測定・選択・集約・統計・図・出力・再生の契約ごとに、版、意味、互換性、過去の結果をどの定義で再生するかを、WP0 で[計算仕様](../../methods.md)に置き、主担当が管理する。版の番号は主担当が割り当てる。
- **マージの順序**は §3 の前提に従い、主担当が PR の説明に書く。順序が変わった場合は、関係する契約と結合の試験をやり直す。マージと公開は、従来どおりオーナーが判断する。
- 作業の前と PR を出す前に `origin/main` を取り込み、影響する検証をやり直す。

## 5. 相互レビュー

| 段階 | 内容 |
|---|---|
| 仕様のレビュー | WP0 の契約と計算の仕様を、主担当が書き、補助が科学的な定義・欠測の扱い・検証のしやすさの観点でレビューする。仕様そのものの誤りを見つける工程で、実装との照合とは分ける |
| 参照値の固定 | WP3・WP4 の参照値は、実装していない側が、実装と期待出力を読む前に、固定した仕様から作ってコミットする。参照計算に、製品の集約・統計の関数を使わない。事例には、試料・視野の数が不均等な場合、ゼロと欠測、欠けた対、群の順序の反転、しきい値の境界、同順位と差が 0 の対を含める |
| 着手前 | 担当が、WP の範囲・変更するファイル・受入の試験を PR の下書きに書き、相手側が範囲の重なりを確かめる |
| PR の提出前 | 担当が [CONTRIBUTING](../../../CONTRIBUTING.md) の検査を実行し、結果を PR に書く |
| コードのレビュー | 参照値が固定された後に、相手側が、要件 ID との対応、科学的な約束（原画像、共通実装、n、除外）、試験の妥当性、非公開データの混入を確かめ、重大度（修正必須／推奨／質問）と根拠を付けて PR のコメントに残す |
| ローカルでの受入 | 統合後の固定したコミットで、補助がローカル版の流れを確かめる（WP11） |
| オーナー | 両者のレビューが終わった PR を確認し、マージする。意見が分かれた点はオーナーが決め、PR に記録する |

- エージェントどうしのレビューは、人によるレビューの承認や、研究者による評価（C9・C10）とは別に記録する。
- CI の成功、ローカルでの動作、出典との照合、研究者の評価、公開は、それぞれ別の事実として報告する。
- 引き継ぎと進み具合は、PR の説明と [roadmap](../../roadmap.md) に記録する。セッションごとの引き継ぎ文書は作らない。

## 6. 運用の決定（2026-10-25）

- 補助は、オーナーの実装依頼に基づき、`codex/…` ブランチへの push と、ドラフト PR の作成・コメントを行う。マージと公開は行わない。
- WP8 の公開データの取得は、接続できる環境で行う。補助の環境から取得できない場合は、補助が URL と期待するハッシュを用意し、主担当がクラウド環境で取得して照合する。
- WP7・WP11 のための Fiji と Cellpose は、リポジトリの固定版の手順で補助の環境に導入し、導入できたかを WP7 で報告する。
- WP3・WP4 は、主担当が WP0 をコミットし、オーナーがその SHA を補助に伝えてから始める。それまでの補助の作業は WP7・WP8 とする。
