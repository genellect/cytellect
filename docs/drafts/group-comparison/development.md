# 群間比較の UX 改善：開発体制（案）

作成：2026-10-25。**独立レビュー前の案です。** [目標定義書](goals.md)と[要件定義書](requirements.md)を、Claude Code と Codex の 2 つのエージェントで並行して実装するときの分担・衝突の防ぎ方・相互レビューを定めます。[チーム開発ルール](../../team-development.md) §5 と [AGENTS.md](../../../AGENTS.md) を前提にし、これらと食い違う場合はそちらに従います。

## 1. 役割

| 役割 | 担当 | 責任 |
|---|---|---|
| オーナー | `@genellect` | 優先順位、要件の確定、マージ、公開 |
| 主担当 | Claude Code | 全体の設計、要件と API の契約、画面、統合、公開デモの組み立て、文書の整合、PR の作成と進行管理 |
| 補助 | Codex | 独立レビュー、範囲を区切った実装（解析パッケージの新しい指標、公開データの取得と検証）、独立した参照計算、ベンチマーク |

主担当が作業の分割と順序を決め、補助に割り当てます。補助が分割や順序に異論を持つ場合は、着手前に PR のコメントかオーナーへの報告で示します。

## 2. 分担の考え方

分担は、モデルの得意・不得意の推測ではなく、作業の性質で決めます。下の割り当ては仮説で、独立レビューで見直します。

| 作業の性質 | 担当 | 理由 |
|---|---|---|
| 画面の大きなコンポーネントにまたがる変更、API の契約、統合 | 主担当 | 文脈が広く、分けると衝突と不整合が増える |
| 入力・出力と受入の試験が明確な、独立した部品（新しい指標の計算、取得用のスクリプト） | 補助 | 新しいファイルで完結し、試験で正しさを確かめられる |
| 独立性が価値になる作業（参照計算、レビュー） | 実装していない側 | 同じ担当が実装と照合を行うと、同じ誤りを見逃す |
| 時間のかかる測定（メモリ・時間のベンチマーク、公開データの取得） | 補助 | 主担当の作業を止めずに並行できる |
| 生成物（公開デモの seed・snapshot、OpenAPI、TypeScript の型、ロックファイル） | 主担当だけ | 手で統合できず、2 か所で作ると必ず衝突する |

## 4. 衝突を防ぐ規則

### 4.1 ブランチと作業場所

- 1 つの WP を 1 つのブランチ・1 つの worktree・1 つの PR で行う。主担当は `claude/…`、補助は `codex/…` を使う。
- 互いのブランチには push しない（チーム開発ルール §3）。直してほしい点は PR のコメントで伝える。
- 作業の前と PR を出す前に `origin/main` を取り込み、影響する検証をやり直す。

### 4.2 ファイルの所有

| ファイル | 所有 | 他方が変えたい場合 |
|---|---|---|
| `apps/web/src/components/workspace/**`（特に `ConnectedWorkspace.tsx`、`ConnectedResults.tsx`）と CSS | 主担当 | PR のコメントで提案する |
| `packages/contracts/**`、`packages/analysis/src/cytellect_analysis/*contracts*.py`、OpenAPI、`apps/web/src/lib/generated.ts`、既定レシピ | 主担当 | 必要な型を PR のコメントで依頼する |
| WP3・WP4 で新しく作る解析パッケージのモジュールと、その試験 | 補助 | PR のコメントで提案する |
| `uv.lock`、`pnpm-lock.yaml` | 主担当（依存の変更だけの PR で） | 必要な依存を依頼する |
| `apps/web/public/showcase/**`、`services/showcase/**` | 主担当 | 依頼する |
| `fixtures/public/**` の新しいデータ | 補助（WP7） | ― |
| `docs/requirements.md`、`docs/roadmap.md`、この下書き | 主担当 | 文案を PR のコメントで示す |
| `docs/methods.md` | 各 WP の担当が、自分の指標の節だけ | 他の節は変えない |

### 4.3 順序と結合

- **契約を先に決める。** WP0 をマージしてから並行作業を始める。並行中に契約を変える必要が出たら、主担当が契約だけの PR を先に出し、両者が取り込む。
- **新しい機能は新しいファイルに書く。** WP0 で指標の登録口を用意し、補助は共有ファイルを編集せずに、新しいモジュールを登録口へ加える。
- **版の番号は主担当がまとめて決める。** 測定・統計の版（[計算仕様](../../methods.md)の protocol の版）を、2 つの PR が同じ番号で使わないようにする。
- **生成物は手で統合しない。** 衝突したら、マージ後の状態から所有者が作り直す。
- **マージの順序**は §3 の前提に従い、主担当が PR の説明に書く。1 つマージされるたびに、他のブランチは `main` を取り込む。

## 5. 相互レビュー

| 段階 | 内容 |
|---|---|
| 着手前 | 担当が、WP の範囲・変更するファイル・受入の試験を PR の下書きに書き、他方が範囲の重なりを確かめる |
| PR の提出前 | 担当が [CONTRIBUTING](../../../CONTRIBUTING.md) の検査を実行し、結果を PR に書く |
| 相互レビュー | 他方が、要件 ID との対応、科学的な約束（原画像、共通実装、n、除外）、試験の妥当性、非公開データの混入を確かめ、PR のコメントに残す。重大度（修正必須／推奨／質問）と根拠を付ける |
| 参照計算 | 新しい指標と統計は、実装していない側が仕様から期待値を作る（WP9） |
| オーナー | 両者のレビューが終わった PR を確認し、マージする。意見が分かれた点はオーナーが決め、PR に記録する |

- レビューする側は、相手のブランチを書き換えない。指摘は PR に残し、担当が直す。
- エージェントどうしのレビューと自動検証は、研究者の評価（[目標定義書](goals.md)の C9・C10）の代わりにしない。
- 引き継ぎと進み具合は、PR の説明と [roadmap](../../roadmap.md) に記録する。セッションごとの引き継ぎ文書は作らない。

## 6. 未決の点

- Codex の実行環境で、Fiji・Cellpose の実行や公開データの取得（ネットワーク）ができるか。できない場合、WP6・WP7 の担当を見直す。
- 補助が GitHub に PR を出し、コメントできる権限の設定。
- WP4 の一文を API で作るか（数値の正本と同じ場所）、画面で保存した値から組み立てるか。要件 S-06 は、どちらの場合も数値を計算し直さないことを求めている。
