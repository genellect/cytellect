作成：2026-11-12。[要件定義書（案）](requirements.md)の実装の手順と、作業の分け方。要件と食い違う場合は要件が正しく、この文書を直す。

## 1. 作業を始める前に

- [AGENTS.md](../../../AGENTS.md)、[要件定義書（案）](requirements.md)、[群間比較の要件定義書](../group-comparison/requirements.md)の §4.4（S-01〜S-08）と §4.7（X-01〜X-06）、[公開デモ](../../showcase.md)を読む。
- 要件定義書の [§8](requirements.md#8-オーナーの判断が必要な点) の判断が決まっていない作業は始めない。下の表の「始められる条件」を確かめる。
- ブランチは最新の `origin/main` から作る。名前は[チーム開発ルール](../../team-development.md#2-開発の流れ)の手順 2 に従う。
- マージ、本番への反映、有料サービスの利用は、オーナーが明示した場合だけ行う。

## 2. 作業の単位

5 つに分ける。WP1 と WP2 は同じファイルを触るので、1 人（1 エージェント）が 1 つの PR で行う。

| WP | 内容 | 要件 | 始められる条件 | 主に触る場所 |
|---|---|---|---|---|
| WP1 | 結果の結論を、見出し・箇条書き・根拠の表示にする | RS-01〜RS-08 | すぐ | `apps/web/src/lib/result-summary.ts`、`ConnectedResults.tsx` |
| WP2 | 前提の表示を 1 か所にする | NT-01〜NT-07 | すぐ（WP1 と同じ PR） | 同上 |
| WP3 | 核小体の場面を最初の場面にし、核ごとの表で開く | DM-02〜DM-04 | 判断 1 | `services/showcase/`、デモの記録、`showcase.spec.ts` |
| WP4 | 新しい場面（オキサリプラチンとシスプラチン） | DM-01、DM-05〜DM-10 | 判断 2・4・5・6・7 | `services/showcase/datasets/`、デモの記録 |
| WP5 | 考察（LLM） | AC-01〜AC-09 | 設計と契約はすぐ。呼び出しは判断 3 | `packages/analysis/`、`services/api/`、`services/proposal-worker/`、`ConnectedResults.tsx` |

### 順序と並行

```
WP1+WP2（画面の文）──────────────► PR A（デモの記録は作り直さない）
WP3（最初の場面）────► PR B（デモの記録を作り直す）
                          └► WP4（新しい場面）──► PR C（デモの記録を作り直す）
WP5 設計・契約 ─────────────────► PR D（呼び出しは許可の後）
```

- **PR A と PR B は並行できる。** 触るファイルが重ならない（PR A は統計の画面の部品と文、PR B は場面の定義と記録）。ただし、どちらも `apps/web/tests/showcase.spec.ts` を触る。後からマージする側が `main` を取り込み、試験を合わせる。
- **デモの記録の作り直しは、同時に 1 つだけ行う。** 記録は公開ファイル全体（約 1 万ファイル）を書き換えるので、2 つの PR が同時に作り直すと、必ず競合する。PR B と PR C は順に行う。
- **PR A は記録を作り直さない。** 結論の文は、ブラウザが保存した推定値から作る。記録した応答は変わらない。フォントの部分集合だけ作り直す（[§7](#7-共通の検証)）。
- WP5 の画面の部品は `ConnectedResults.tsx` を触るので、PR A のマージ後に始める。

### 手順

1. **型を決める。** `ResultSummary` を次の形にする。
   ```ts
   interface ResultSummary {
     heading: string;                       // RS-02
     points: string[];                      // RS-03（最大 4）
     basis: {label: string; reason: string | null; action: "experiment" | null}; // RS-04、NT-01
     missing: string | null;                // RS-07
     cautions: string[];                    // NT-05 の「常に出す」だけ
     notes: string[];                       // NT-05 の「折りたたみの中」
   }
   ```
2. **`summarize()` を書き換える。** 今の `conclusion` を作る分岐（検定あり、記述で一致、記述で不一致、違いが不明確、順位に基づく検定）を、そのまま見出しの分岐にする。文末の「〜でした」「（記述のみ・検定なし）」を外し、RS-02 の形にする。
3. **箇条書きを作る。** `estimates`（群の値、差・比、区間、`runs`）から、RS-03 の 4 項目を作る。数値の書式は、今の `formatNumber()` を使う。
4. **根拠の表示を作る。** 手法の名前、n、p 値を「·」でつなぐ。記述統計の場合は、理由（`explanations`）と、次の行動を持たせる。
5. **注意を分ける。** 今の `cautions` を、NT-05 の表に従って `cautions` と `notes` に分ける。API の警告（`comparisonWarnings`、`commonWarnings`）も、同じ表で分ける。
6. **`ResultSummaryCard` を並べ替える。** 見出しは `<h3>`、箇条書きは `<ul>`、根拠の表示は `<details>`（閉じた状態が 1 行）にする。`notes` は「解析上の注意」の折りたたみに入れる。
7. **設定の領域を直す**（NT-03、NT-04）。
8. **`RunMedians` を同じ並びにする。**
9. **試験と文書を更新する**（下）。

### 文の規則を変えないこと

- 向きは「処理 − 対照」。計算上の群の順序が逆なら、符号と区間の端を入れ替える（S-04）。
- 順位に基づく検定で p < 0.05 のときの向きは、保存した効果量と群の順序から決める。実験回の多数決や平均から決めない（S-01、#195 のレビュー）。
- 割合の差は「ポイント」で書く。保存した値は、すでに 100 倍されている。
- 群名と日本語の間の空白：英字・数字で終わる群名の後に助詞が続く場合は、半角の空白を入れる（#195 のレビューの指摘。この PR で直す）。

| 段階 | 内容 | 終わりの条件 |

| 5. 記録と公開ファイル | デモの記録を作り直す。公開ファイルを上限に収める（判断 6） | C-23〜C-26 |

### 今のデータの定義の形

`services/showcase/datasets/zenodo-6643470-nucleolar.json` を手本にする。主な項目：

- `dataset`：出典、DOI、ライセンスの原文（`license_quoted`）、帰属の表示、改変の内容、`reported_change`（出典の報告。画面の「出典の報告と、このデモでの測定」に出る）
- `selection`、`crop_rule`：視野と切り出しの規則（測定値に依存しない）
- `fields`：視野ごとのチャンネルと、条件・実験回・撮影日
- `experiment`：群、対照、実験回、`independence_confirmed`
- `scenario`：核小体の定義、背景補正、統計の比較、`direction_checks`、`gate_channels`

場面を 2 つ（オキサリプラチン、シスプラチン）にする場合は、定義も 2 つにする。未処理の視野は、両方の場面で同じファイルを使う。

### 検出を動かす場所（判断 5）

- 核の検出は Fiji 上の StarDist。この開発環境（クラウドのセッション）には Fiji がない。
- 核小体（NPM1 による定義）と核質は Python だけで決まり、検出エンジンは要らない。
- 推奨：GitHub Actions に、手動で起動するジョブを足す。`scripts/fiji_setup.py`（CI の `fiji-browser` と同じ）で Fiji を用意し、ビルドの `prepare` と `scenario` を実行して、検出の記録を成果物として保存する。以後のビルドは、その記録を再生する。
- ジョブを足すのは CI の変更なので、別の PR にする。

### 守ること

- 結果を見てから、濃度・指標・視野を選び直さない（Q-03、X-04）。段階 2 で決めたものを測る。
- 核の大きさに依存する除外（断片の削除など）を、自動で使わない（Q-03）。
- 出典の向きと合わない結果を、合うように見せない。
- 新しい画像は、`fixtures/public/allowlist.json` に SHA-256 とともに登録する（D02）。

## 6. デモの記録の作り直し

[公開デモ](../../showcase.md)の手順に従う。ここには、2026-11-11 の作り直し（#194、#196、#197）で分かった注意だけを書く。

- **段階**：`prepare` → `scenario` → `grid` → `publish` → `snapshot` → `journal` → `qa`。場面の定義を変えたら `scenario` から、画面や記録用の手順だけを変えたら `journal` から実行する。
- **検出を動かさない**：`--fiji` に、呼ばれると終了コード 97 で止まる仮の実行ファイルを渡す。記録にない検出が要求されると、ビルドが止まる。GPU 推論と LLM の接続情報（`CYTELLECT_CELLPOSE_REMOTE_*`、`CYTELLECT_PROPOSAL_*`）は、環境から外す。
- **作業ディレクトリ**：取り込んだ画像、初期状態、検出の記録は、チェックアウトの外の作業ディレクトリ（`--work`、`--cache`）にある。リポジトリには入っていない。検出の記録は、公開している `seed.zip` の `recordings/` にも入っている。新しい環境で作り直す手順（`seed.zip` から検出の記録を戻す方法）は、WP3 で確かめて[公開デモ](../../showcase.md)に書く。
- **時間**：`journal` は 233 場面で約 105 分（2026-11-11）。進み具合は、ビルドのログに 1 場面ごとに出る。
- **依存パッケージ**：`journal` は、チェックアウトの中で web をビルドする。`node_modules` は、そのチェックアウトで `pnpm install` したものを使う（ほかのチェックアウトへのリンクでは失敗する）。
- **ビルドが書き換えるファイル**：`apps/web/next-env.d.ts` と `apps/web/tsconfig.json` は、記録用のビルドが書き換える。コミットしない（元に戻す）。
- **記録の順に依存する操作**：訪問者の操作は、記録した順と一致したときだけ、記録から答える。記録用の手順を足すときは、操作の前に、領域や設定を明示して選ぶ。試験は、記録したときと同じ順と待ち方で書く。
- **完了の条件**：記録したときの警告 0 件、コンソールエラー 0 件。`showcase.spec.ts` が通る。

## 8. WP5：考察（LLM）

解析提案（[解析提案のサービス](../../proposal-service.md)）と同じ経路と、同じ守り方を使う。

```
ブラウザ → API  POST /v1/jobs/{結果のジョブ}/discussion
            API が、保存した結果から送る内容を作る（画像・ファイル名・パスを含めない）
          → 提案サービス（Cloudflare Worker + D1）POST /v1/discussions
            → LLM（構造を決めた出力、保存しない設定）
          ← 下書き → API が検証（数値の照合、禁止した表現）→ 保存 → 表示
```

### 段階

| 段階 | 内容 | 有料 API |
|---|---|---|
| 1. 契約 | `packages/analysis/` に、送る内容（`DiscussionContext`）と出力（`DiscussionDraft`）の契約を置く。版は `result-discussion/1.0.0`。出力は AC-04 の 3 つの見出しと、各項目が根拠にした数値への参照 | 呼ばない |
| 2. 検証 | 出力の数値を、送った結果の数値と照合する関数。禁止した表現（AC-05）を落とす関数。単体試験 | 呼ばない |
| 3. API | 送る内容を、保存した結果から作る経路。考察の保存（結果のジョブ、モデル、プロンプトの版）。上限と失敗の扱い（L04〜L06） | 呼ばない（サービスは模擬） |
| 4. 画面 | 「考察」の枠（AC-01、AC-02、AC-06）。有効にしていない利用者への 1 行 | 呼ばない |
| 5. サービス | 提案サービスに、考察の経路とプロンプトを足す | **判断 3 の後** |
| 6. デモ | ビルドのときに一度だけ考察を作り、記録する。オーナーが内容を確かめる（AC-08） | **判断 3 の後** |

### プロンプトの方針

- 入力は、結論（A）の値と、実験の記述だけ。
- 「計算した値を言い換えない。新しい数値を作らない。文献を挙げない」を指示し、出力の検証でも確かめる（指示だけに頼らない）。
- 記述統計の結果では、「〜の可能性がある」「〜と整合する」の語彙に限る。
- 出力は日本語。利用者の言語の設定が入ったら、それに合わせる。

### 決めること（設計のときに、オーナーに確認する）

- 考察を、利用者が編集できるか。初版は、編集なし・作り直しだけを推奨する。
- 実験の目的を、どこで入力するか。「実験」の画面に 1 つの欄を足す案を推奨する。
- 文献の参照を出すか。初版は出さない（捏造を防ぐため）。

## 9. 危険と対策

| 危険 | 対策 |
|---|---|
| 短くした結論が、前提を隠したように見える | 根拠の表示を常に見える 1 行にする。保存する結果・CSV・Methods には、これまでどおり前提を書く（NT-07）。C-06 で、検定をしていないことを確かめる |
| 新しい場面で、出典の向きと合わない | 段階 2 で比較を記録し、段階 4 でオーナーが扱いを決める。合うように条件を選び直さない |
| オキサリプラチンの効果が、1 時間・10 µM では画像で分かりにくい | 段階 1 で、論文の図の濃度を確かめる。分かりにくい場合は、D-10 (c) を満たさないので、第二候補（DM-08）を検討する |
| 公開ファイルが大きくなる | 判断 6 の上限。場面を足す PR で、記録の範囲を見直す |
| 考察が、誤った生物学を述べる | 数値の照合と禁止した表現の検証（AC-05）。計算した値と分けた表示（AC-01）。デモの考察は、オーナーが確かめてから公開する（AC-08） |
| 2 つの PR が、同時にデモの記録を作り直して競合する | [§2](#2-作業の単位) の順序。作り直しは 1 つずつ |

## 10. 迷ったときの判断の基準

- 文を足して解決しない。見出し、箇条書き、表、図で伝える。説明が要る場合は、開いて読む形にする。
- 同じことを 2 回書かない。前提は 1 か所。
- 計算をブラウザに足さない。足りない値は、API と共通の解析が保存する。
- 科学的な点（比較の向き、指標、条件、視野の選び方、検定の可否）で迷ったら、実装を止めてオーナーに確認する。
- デモだけの画面や文を作らない。本番と同じ部品で、素材を替えて伝える。
