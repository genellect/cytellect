# 開発の原則

Cytellect の開発で、人も AI エージェントも守る原則。作業の前に関係する節を必ず読み、判断に迷ったときはここに立ち返る。開発の進め方は[チーム開発ルール](team-development.md)、開発環境の構築と起動は [CONTRIBUTING](../CONTRIBUTING.md) にある。

## プロダクトの使命

| 層 | 内容 |
|---|---|
| 使命 | 画像解析を、一部の専門家の技術から、すべての生命科学研究者が使える研究基盤に変える |
| プロダクト | 画像解析に詳しくない Wet 研究者が、何を対象に何を測っているかを理解し、明確な導線のもとで迷わず修正と判断を行い、統計と編集可能な論文の図まで同じ作業の中で完了できる |
| 事業 | オープンソースで信頼を得て、研究室単位のクラウドで収益を得る |
| LP | 画像を扱う研究者全体に、自分の研究を論文に届ける志と、科学の未来に参加したいという感情を起こし、デモと導入へつなぐ |

### 重点

- UX/UI デザインの継続的な改善
- 研究室の実画像での実証
- 検出モデルの追加学習と評価基盤の構築
- LLM による解析支援基盤の構築
- クラウド費用と有料 API のコストの最適化
- 解析基盤のクラウド（AWS、Hugging Face、Modal）への移行と、完全な Web アプリ化

### 約束

- 数学的な妥当性以上に、生物学的な妥当性を重視する。
- 秘密情報と研究データを守る。
- 本番環境を壊さない、保守しやすい開発 UX を保つ。
- README、AGENTS.md、チーム開発ルールをはじめとする文書は、人も読む文章として書く。要点を簡潔に整理し、人と AI エージェントが迷わず参照できる導線にする。
- 方針・仕様・手順を変更するときは、関連する文書をすべて同じ変更で更新し、文書間に矛盾を残さない。

## 計算とデータの整合性

- 測定値と統計は、API と解析パッケージの共通実装だけが生成する。ブラウザや配布形態ごとに別の計算を持たない。
- API を変えたら、OpenAPI、既定レシピ、生成した TypeScript 型を同じ変更で更新する。
- 原画像の画素値を変えない。検出用の前処理と表示用の色・明るさは、測定から分離する。
- マスクの正本は、原画像座標のラベル画像とする。核を編集したら依存する核小体を、マスクや除外を変えたら派生する統計・図を無効化し、古い結果を混在させない。
- 閾値・背景補正・対象選別・計算式・統計手法を変えるときは、レシピと処理の版、[Methods](methods.md)、数値テストを同時に更新する。
- 欠測とゼロ、核・核小体・視野・試料・独立した実験単位を区別する。有意差を得るための調整と、失敗した視野の無断除外をしない。

## 研究データと検証

- 非公開の画像・論文・ファイルパス・研究結果・参加者情報と、認証情報・トークンを、コード・ログ・Issue・PR・スクリーンショット・CI・外部 AI に含めない。
- 実行時のデータは checkout の外に置き、開発に本番の認証情報を使わない。非公開データの検証は別に行い、公開するのは承認済みの匿名化した報告に限る。
- 合成データは再現可能な数値テストに使う。画像の結合テストと公開デモには公開実画像を使い、出典・染色情報・再配布条件・ハッシュを記録する。別の染色を NCL や GFP として扱わない。
- 検出精度と使いやすさは、実画像と研究者の操作で評価する。文献の仮説と、利用者に確認した要望を区別する。
- CI の成功や p 値の一致は、生物学的な妥当性の証明ではない。評価は失敗・欠測・未検証の範囲も含めて報告する。
- 検出モデルの評価には、学習と条件調整に使わない実験回の画像と、研究者が描いた輪郭を使う。指標は再現率・適合率・F1、融合・過分割の数、面積・輝度の誤差とし、実験回ごとに集計する。
- 学習データ・重み・推論条件は組にして版を管理する。非公開データで学習した重みの公開には、オーナーとデータ提供元の承認が要る。

## モデル・依存関係・外部サービス

- 依存の版とモデルのハッシュを固定し、コード・重み・データのライセンスをそれぞれ確認する。
- 解析の実行時に、パッケージやモデルの取得、任意コード・マクロの実行、外部 URL からの画像取得をしない。
- LLM の解析提案は既定で無効とし、利用者が有効にした場合に限り、[定義された範囲](workspace-redesign.md#analysis-proposal-service-llm)の情報を送る。これは製品の機能であり、開発用 AI や CI に研究データを渡してよい根拠にはならない。
- 提案は構造化した設定としてローカルで検証し、測定・統計には共通の計算処理を使う。有料の呼び出しには運用者が設定した予算が要る。詳細は [security.md](security.md) に従う。
- 外部送信・設定変更・公開・課金は、ユーザーの現在の許可に従う。有料サービスや外部の基盤（AWS、Hugging Face、Modal など）の採用・移行は、オーナーの判断を経て別の変更として進める。

## 問題への対処

- **原因は証拠で特定する。** 不具合やエラーの原因は、ログ・ソースコード・再現結果などの具体的な証拠から特定する。推測を根拠に結論を出さない。証拠が得られない場合は「未確定」と明記し、推測と事実を区別して報告する。
- **対症療法で直さない。** 個別の事例に合わせた規約・プロンプトの文言・例外分岐を足すと、同じ型の事例が出るたびに規約が増え、品質が下がる。修正の前に、その失敗の一般形を特定し、次の順で対処する。
  1. 既存の一般則で扱えるなら、新しい規則を足さない。
  2. 一般則がなければ、個別の対症ではなく一般則や構造で対処する。判定・構造・不変条件は、コードの決定論的な検査で守る。

## 画面と文章

- LP の基準は[現在の採用文](../apps/web/src/components/PublicLanding.tsx)と [interface-design.md](interface-design.md)、見た目と素材の正本は [LP の美術方針](lp-art-direction.md)（2026-10-23 承認）とする。
- LP は写真・文字・構図・実際の出力を中心に据える。開発バッジ、防御的な注釈、素材写真の断り書きを足さない。機能・実績・推薦を創作しない。
- 画像・映像の出典は、フッターの折りたたみのクレジットに、素材ごとの作者と配布元へのリンクで示す。ライセンスが求める場合は、ライセンスと加工の内容も書く。
- 明るい背景と読みやすい文字・CTA を保ち、サイエンスと世界観は実写級の実験室の映像で表す。手作りの造形、細胞や分子の可視化、暗色・青を基調とする以前の配色を主役に戻さない。
- 素材は、種類ではなく、実写級であること・心を動かすこと・雰囲気が合っていることで判定し、出典と加工内容を来歴に記録する。省モーション設定と読み込み失敗時は、同じ映像の静止画を出す。Lila は映像・光・余白・タイポグラフィの品質の参照にとどめ、配色や素材の指定として扱わない。
- アプリでは明確な操作名と短い説明を使い、[一つのワークスペース](workspace-redesign.md)で画像から図まで進める。視野ごとの確認手順を増やさず、研究者の目的から必要な操作を設計する。Fiji との比較は、実際の機能を確認して書く。

## 開発環境とリリース

- 通常の開発はクラウドのエージェント環境（Codex Cloud、Claude Code など）で行い、合成の数値データと登録済みの公開データで検証する。環境構築・実機確認・非公開データの検証は、データの境界を守ってローカルで行える。
- 調査は対象を絞り、複数人・複数エージェントで作業するときは編集範囲を分ける。影響のない検証を繰り返さず、必須 CI は維持する。
- ローカル版は共通の解析基盤を動かす実行環境。起動・インストーラー・セッション・保存期限を変えるときは [local.md](local.md) を確認し、ホスト型 API と同じ解析の実装を保って、完全な Web アプリ化を見据える。
- 配布には対象パッケージの数値検証と導入後の受入確認、公開には正規 URL での動作確認が要る。Fiji や非公開データの検証を省いた場合は、未実施と記録する。
- README には確認済みの状態を書き、未完了の要件は [roadmap](roadmap.md) に残す。[research-workflow.md](research-workflow.md) は研究者の操作と評価の背景として参照し、日付付きの記録は現在の方針・実装と照合する。
